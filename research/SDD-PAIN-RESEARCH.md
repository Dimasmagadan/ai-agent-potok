# SDD: Исследование болей рекрутеров в открытых сообществах

Дата постановки: 2026-08-18. Заказчик: Дмитрий. Исполнитель: автономный агент (простая модель) с доступом к веб-поиску и загрузке страниц.

## Цель

Собрать из публичных форумов, каналов и сообществ рекрутеров список часто обсуждаемых болей и проблем, кластеризовать их по частоте, затем определить, какие из них решаемы в рамках конкурса AI-агентов «Потока». Результат ляжет в выбор финальной конкурсной идеи (см. `../BRAINSTORM-FINAL.md`, читать его НЕ нужно — весь необходимый контекст вшит ниже).

## Артефакты (что должно появиться)

Все файлы создаются в каталоге `research/pains/` относительно корня репозитория:

| Файл | Этап | Содержимое |
|---|---|---|
| `sources.md` | 1 | Таблица проверенных источников |
| `failures.md` | 1–2 | Лог недоступных/пустых источников |
| `pains-raw.md` | 2 | Сырые записи болей с цитатами и URL |
| `pains-clustered.md` | 3 | Кластеры болей с частотами |
| `PAIN-RESEARCH-REPORT.md` | 4–5 | Итоговый отчёт с маппингом на конкурс |

## 0. Вшитый контекст (прочитать, запомнить, никуда не ходить)

**Конкурс:** AI-agent contest от рекрутинговой ATS-платформы «Поток». Дедлайн 6 сентября 2026 (~2,5 недели). Требования: решение HR-задачи, open source, воспроизводимость для проверяющих (демо на обезличенных данных). Запрещено в MVP: автоматический отказ кандидату, автоматическое перемещение по этапам, использование чувствительных признаков (возраст, пол, фото).

**Что умеет API «Потока»** (это нужно для этапа 4 — маппинга):

- читать/создавать/обновлять вакансии и кандидатов;
- искать кандидатов по имени, телефону, email (только точный поиск, семантического нет);
- получать резюме и карточку кандидата;
- видеть и менять этап кандидата в воронке;
- читать историю событий (`events_stream`): комментарии, звонки, встречи, смены этапов;
- писать комментарии в карточку кандидата, прикреплять документы;
- работать с календарём интервью и напоминаниями;
- получать причины отказов;
- получать штатное расписание и заявки на подбор (модуль может быть отключён);
- показывать вакансии и принимать отклики через публичный Career API;
- вебхуки существуют, но их включает только команда «Потока» (не рассчитывать на них).

**Чего API НЕ умеет:** AI-анализ (делает внешний агент), семантический поиск по резюме, интеграция с hh.ru/LinkedIn, доступ к рынку кандидатов вне своей базы, парсинг чужих сайтов.

**Уже известные боли** (из интервью со знакомым рекрутером, 2026-08-18): (а) контроль прохождения испытательного срока; (б) поиск по базе кадрового резерва по навыкам. Задача исследования в том числе — проверить, насколько эти две боли частотны в широкой выборке.

## 1. Правила для исполнителя (обязательные, нарушение = брак)

1. **Ничего не выдумывать.** Каждая боль подтверждается реальным URL и дословной цитатой. Если цитату нельзя скопировать (видео, картинка) — писать пересказ с пометкой `[пересказ]`.
2. **Недоступный источник — не проблема.** Страница не открылась, требует логин, пустая — одна строка в `failures.md`, идти дальше. Никогда не останавливаться из-за одного источника.
3. **Работать строго по этапам** (1 → 2 → 3 → 4 → 5). После каждого этапа сохранить его файл-артефакт, только потом начинать следующий.
4. **Не включать в артефакты ФИО и ники авторов постов.** Только URL, цитата, роль («рекрутер», «HRD», «кандидат» — если понятна из контекста).
5. **Не оценивать и не фильтровать боли на этапах 1–2.** Записывать всё, что подходит под определение боли (см. этап 2). Отбор — только на этапах 3–5.
6. **Язык всех артефактов — русский.** Цитаты из англоязычных источников — оригинал + перевод.
7. **Лимиты:** этап 1 — максимум 25 источников; этап 2 — максимум 60 записей (минимум 30); если лимит достигнут — этап завершён досрочно, это нормально.
8. Даты относительные («на прошлой неделе») конвертировать в абсолютные, исходя из даты публикации поста.

## 2. Этап 1 — Сбор источников

### 2.1. Стартовый список (проверить каждый)

Открыть каждый, убедиться, что там есть живые обсуждения рекрутеров (посты + комментарии), занести в `sources.md`:

1. `vc.ru` — раздел HR (`vc.ru/hr`), поиск по разделу по словам «рекрутер», «подбор».
2. `habr.com` — хаб «Управление персоналом», статьи с комментариями.
3. `journal.tinkoff.ru` — сообщество, темы про работу рекрутером.
4. `hh.ru/articles` — статьи для HR с комментариями.
5. `huntflow.ru/blog` — блог конкурирующей ATS (боли, которые они описывают, — проверенные рынком).
6. `hr-portal.ru` — форум, разделы про подбор персонала.
7. `e-xecutive.ru` — сообщество, ветки про HR/подбор.
8. `pikabu.ru` — поиск «рекрутер», истории из практики с комментариями.
9. `reddit.com/r/recruiting` — топы за год.
10. `reddit.com/r/recruitinghell` — взгляд кандидатов на провалы рекрутинга (боли зеркальны).
11. Telegram-каналы и чаты про рекрутинг: искать через `tgstat.ru` по словам «рекрутинг», «подбор персонала», «HR». Брать каналы с открытым архивом постов (читать через веб-версию `t.me/s/<имя_канала>`).

### 2.2. Поисковые запросы (выполнить все, по каждому взять топ-5 результатов)

Русские:

1. `что бесит рекрутеров в работе`
2. `рутина рекрутера сколько времени уходит`
3. `боли рекрутера автоматизация подбора`
4. `рекрутер отчёты для руководства сколько времени`
5. `как рекрутеры ведут кадровый резерв на практике`
6. `испытательный срок контроль нового сотрудника HR процесс`
7. `нанимающий менеджер не даёт обратную связь по кандидату что делать`
8. `кандидат пропал перестал отвечать рекрутеру`
9. `разбор откликов вручную рекрутер устал`
10. `дубли кандидатов в базе ATS проблема`
11. `чего не хватает в ATS рекрутеру форум`
12. `массовый подбор проблемы рекрутера`

Английские:

13. `recruiter biggest daily pain points forum`
14. `what recruiting tasks would you automate reddit`
15. `ATS frustrations recruiters complain`
16. `hiring manager feedback delay recruiter vent`
17. `talent pool database nobody uses recruiting`

### 2.3. Критерии отбора источника

Источник попадает в `sources.md`, если выполняются все три условия:

- есть высказывания практикующих рекрутеров/HR (посты, комментарии, треды), а не только маркетинговый текст;
- контент открыт без логина;
- обсуждение не старше 2022 года (для форумов допускается старше, если ветка активна).

Рекламные статьи без комментариев — отбрасывать. Статья-обзор болей допустима как источник, но помечается `type: статья` (вес ниже, см. этап 3).

### 2.4. Формат `sources.md`

```markdown
| id | URL | Тип | Название/тема | Почему взят |
|---|---|---|---|---|
| S01 | https://... | форум | ... | живой тред, 40+ комментариев рекрутеров |
```

Типы: `форум`, `статья+комменты`, `статья`, `telegram`, `reddit`, `блог`.

**Готово, когда:** в таблице 15–25 источников, из них не более 5 с типом `статья`.

## 3. Этап 2 — Извлечение болей

### 3.1. Что считается болью

Запись создаётся, если автор (рекрутер/HR, либо кандидат, описывающий провал процесса):

- жалуется на повторяющуюся ручную работу или трату времени;
- описывает регулярную потерю информации, кандидатов, сроков;
- спрашивает «как вы с этим справляетесь / чем автоматизируете»;
- описывает конфликт процессов (менеджер молчит, кандидат пропал, руководство требует отчёт);
- перечисляет, чего ему не хватает в инструментах.

НЕ боль: разовые истории без признака повторяемости («один раз попался странный кандидат»), обсуждение зарплат рекрутеров, юмор без предметной жалобы.

### 3.2. Процедура

Для каждого источника из `sources.md`: открыть, прочитать посты и первые ~30 комментариев, выписать каждую найденную боль отдельной записью. Один источник может дать 0 записей — это нормально, отметить в `failures.md` строкой «S07 — болей не найдено».

### 3.3. Формат записи в `pains-raw.md`

```markdown
### P001
- Источник: S03 (https://прямая-ссылка-на-пост-или-коммент)
- Дата поста: 2025-11-04 (если известна, иначе «не указана»)
- Кто говорит: рекрутер агентства
- Цитата: «Каждый понедельник полдня собираю руками отчёт по воронке для директора»
- Суть одной фразой: ручная еженедельная отчётность по воронке
- Маркеры частоты: «каждый понедельник», «полдня»
```

Поле «Маркеры частоты» — дословные слова о регулярности/затратах («каждый день», «по 3 часа», «постоянно», «уже год»); если их нет — «нет».

**Готово, когда:** 30–60 записей, каждая с URL и цитатой/пересказом, покрыто ≥12 источников.

## 4. Этап 3 — Кластеризация

### 4.1. Таксономия (использовать эти категории)

| Код | Кластер |
|---|---|
| C01 | Sourcing: поиск и привлечение кандидатов |
| C02 | Скрининг: разбор откликов и резюме вручную |
| C03 | Коммуникация с кандидатами (молчание, ghosting, статусы) |
| C04 | Нанимающие менеджеры: медленный фидбек, смена требований |
| C05 | Отчётность и метрики для руководства |
| C06 | База/ATS-гигиена: дубли, устаревшие данные, кадровый резерв |
| C07 | Испытательный срок, онбординг, адаптация |
| C08 | Массовый найм и большие объёмы |
| C09 | Тексты вакансий, employer brand, каналы публикации |
| C10 | Организация интервью: календарь, переносы, неявки |
| C11 | Оффер и выход: отказ после оффера, контроффер |
| C12 | Ручной перенос данных между системами (ATS ↔ таблицы ↔ мессенджеры) |

Если запись не подходит ни в один кластер — создать `C13+` с пометкой `NEW` и коротким названием. Одна запись может попасть максимум в 2 кластера (тогда указывается в обоих).

### 4.2. Подсчёт частоты

Частота кластера = **число разных источников**, в которых он встретился (не число записей: 5 жалоб из одного треда = 1 источник). Записи из источников типа `статья` (без комментариев) считать с весом 0.5.

### 4.3. Формат `pains-clustered.md`

```markdown
| Кластер | Записи | Источников | Балл частоты | Типичная цитата |
|---|---|---|---|---|
| C04 Нанимающие менеджеры | P003, P011, P024 | 6 | 4 | «...» |
```

Балл частоты: 1 источник = 1; 2–3 = 2; 4–5 = 3; 6–9 = 4; 10+ = 5.

Отсортировать по баллу частоты по убыванию.

**Готово, когда:** каждая запись из `pains-raw.md` отнесена к кластеру, таблица отсортирована.

## 5. Этап 4 — Маппинг на конкурс

Для **каждого кластера с баллом частоты ≥ 2** ответить письменно на четыре вопроса (используя ТОЛЬКО список возможностей API из раздела 0):

1. Есть ли нужные данные в API «Потока»? Какие именно endpoint-возможности из списка?
2. Достаточно ли read-only, или нужен write-back / вебхуки / модуль Staffing (то, что может быть недоступно)?
3. Реалистично ли собрать MVP за 2–3 недели одному разработчику?
4. Можно ли показать на демо с обезличенными фейковыми данными (без реального тенанта)?

### Оценка решаемости (0–5, строго по якорям)

- **5** — read-only данных из API достаточно, агент = правила поверх событий;
- **4** — данные в API есть, нужен внешний AI-анализ (LLM/embeddings), read-only;
- **3** — данные частично в API, частично из открытых источников (Career API, публичные страницы);
- **2** — требуется write-back, вебхуки или модуль, который может быть отключён;
- **1** — основные данные живут вне «Потока» (hh.ru, LinkedIn, соцсети);
- **0** — вне зоны API вообще (рынок труда, поведение кандидатов до отклика).

### Оценка демо-потенциала (1–5, по якорям)

- **5** — за 2 минуты понятно без объяснений (алерт в Telegram, наглядный поиск);
- **3** — нужно объяснять контекст, но результат осязаем (отчёт, дашборд);
- **1** — результат абстрактный (методология, рекомендации).

## 6. Этап 5 — Итоговый отчёт `PAIN-RESEARCH-REPORT.md`

Структура (все секции обязательны):

```markdown
# Отчёт: боли рекрутеров и их решаемость в конкурсе «Потока»
Дата: <дата выполнения>. Источников: N. Записей: M.

## 1. Топ болей
| Кластер | Частота (1–5) | Решаемость (0–5) | Демо (1–5) | Приоритет = Ч×Р×Д | Типичная цитата |
(все кластеры с частотой ≥2, сортировка по Приоритету)

## 2. Сверка с интервью знакомого рекрутера
- Испытательный срок (C07): подтвердился / не подтвердился широкой выборкой, частота X, ссылки на записи.
- Кадровый резерв (внутри C06): подтвердился / не подтвердился, частота X, ссылки на записи.

## 3. Топ-3 боли для конкурса
Для каждой: название, почему (частота + решаемость + демо), какие API-возможности
используются, главный риск, ссылки на 2–3 самые яркие цитаты (id записей).

## 4. Боли, которые часто обсуждают, но конкурс их НЕ решит
Список с причиной (решаемость 0–1) — чтобы осознанно не тратить на них время.

## 5. Ограничения исследования
Что не удалось открыть (ссылка на failures.md), перекосы выборки
(например, преобладание агентских рекрутеров или англоязычных источников).
```

Приоритет считать как произведение трёх баллов; при равенстве выше ставится кластер с большей решаемостью.

## 7. Критерии приёмки (проверяет заказчик)

- [ ] `sources.md`: 15–25 источников, ≤5 типа «статья», все URL открываются.
- [ ] `pains-raw.md`: ≥30 записей; выборочная проверка 5 случайных записей — цитата действительно есть по URL.
- [ ] Каждая запись отнесена к кластеру; кластеров с записями ≥8.
- [ ] Частота = число источников, не число записей (проверить на одном кластере вручную).
- [ ] Маппинг: у каждого кластера с частотой ≥2 есть ответы на 4 вопроса и обе оценки с обоснованием по якорям.
- [ ] Отчёт содержит все 5 секций, включая явную сверку с болями знакомого рекрутера.
- [ ] Нигде нет ФИО/ников авторов постов.

## 8. Fallback-инструкции

- Поиск не даёт результатов по запросу → переформулировать один раз (синонимы), затем перейти к следующему запросу.
- `tgstat.ru` недоступен → искать Telegram-каналы обычным поиском: `телеграм канал рекрутинг подбор персонала`, читать через `t.me/s/<имя>`.
- Reddit не открывается → добавить `old.reddit.com` вместо `www.reddit.com`.
- После 2 часов работы этап 1 не завершён → зафиксировать сколько есть (но не меньше 10 источников) и идти дальше.
- Меньше 30 записей после обхода всех источников → вернуться к этапу 2.2, выполнить запросы 1–5 повторно с добавкой слова «телеграм» и «форум», добрать источники.
- Любая неразрешимая ситуация → записать вопрос в конец `PAIN-RESEARCH-REPORT.md` в секцию «Ограничения», продолжить работу. Не останавливаться и не ждать ответа.
