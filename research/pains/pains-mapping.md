# Этап 4: Маппинг болей на API конкурса

Дата: 2026-08-18. Кластеров на маппинг: 6 (с баллом ≥2).

## C02: Скрининг — разбор откликов и резюме вручную (Балл: 3)

### Описание боли
Рекрутеры тратят 80% времени на ручной разбор откликов и резюме. При 300–400 откликах на вакансию за неделю процесс становится непосильным. Рекрутеры разбирают резюме за 6 секунд, часто пропускают подходящих кандидатов из-за усталости. ATS отсеивает 75% резюме из-за форматирования.

### Вопрос 1: Есть ли нужные данные в API?

**Да, полностью.** API позволяет:
- Получить список кандидатов по вакансии (из отклика, истории)
- Прочитать резюме и карточку кандидата
- Видеть этап кандидата в воронке (скрининг, интервью и т.д.)
- Читать историю событий (комментарии, статусы)

**Endpoint-возможности:** `GET /candidates`, `GET /candidates/{id}`, `GET /candidates/{id}/resume`, `GET /events_stream`.

### Вопрос 2: Достаточно ли read-only?

**Да, read-only достаточно.** Агент может:
- Прочитать отклики по вакансии
- Проанализировать резюме по ключевым словам и структуре
- Переместить кандидата в следующий этап (требуется write: `PATCH /candidates/{id}/stage`)
- Написать автоматический скрининг-комментарий (требуется write: `POST /candidates/{id}/comments`)

Минимально: write-back для изменения статуса (переместить в одобренные/отклоненные). **Требуется write для полноценности**, но начальный анализ может быть read-only с рекомендациями.

### Вопрос 3: Реалистично ли MVP за 2–3 недели?

**Да, реалистично.** MVP = агент, который:
1. Получает отклики по вакансии
2. Извлекает ключевые слова и навыки из резюме (простой парсинг текста, не ML)
3. Сравнивает со списком требований из вакансии (простой matching по словам)
4. Выдает рекомендацию (топ N кандидатов для повторного просмотра, отклоненные)
5. Опционально: пишет скрининг-комментарий в карточку

**Сложность:** низкая–средняя. Не требуется семантический поиск или ML-модели. Простая логика на правилах.

### Вопрос 4: Можно ли показать на демо?

**Да, с фейковыми данными.** Сценарий:
1. 3–5 обезличенных резюме (текст)
2. Описание вакансии
3. Агент парсит резюме, выставляет баллы
4. Выводит топ-3 кандидата и отклоненных
5. На экране видна таблица кандидатов с баллами и рекомендациями

---

### **Решаемость: 5** (read-only данные есть, простая логика на правилах)

### **Демо-потенциал: 5** (за 2 минуты видно рейтинг кандидатов, очень наглядно)

## C03: Коммуникация с кандидатами (молчание, ghosting) (Балл: 2)

### Описание боли
Рекрутеры не успевают ответить более чем 50% кандидатам. Кандидаты пропадают после интервью (ghosting). Нет отказов. Система не отслеживает, кто получил ответ, кто нет.

### Вопрос 1: Есть ли нужные данные в API?

**Частично.** API позволяет:
- Видеть события (комментарии, звонки, встречи)
- Прочитать ответ-отказ (если он был)
- Написать комментарий в карточку (требует write)
- Отправить напоминание через интеграцию с календарём (если доступна)

**Endpoint-возможности:** `GET /events_stream`, `GET /candidates/{id}`, `POST /candidates/{id}/comments`, но **нет встроенного функционала для автоматической рассылки отказов кандидатам через email/SMS**.

### Вопрос 2: Достаточно ли read-only?

**Нет, нужен write-back и вебхуки.** Требуется:
- Писать комментарии в карточку (write: `POST /candidates/{id}/comments`)
- Отправлять уведомления кандидатам (требуется внешняя интеграция или вебхуки — **недоступны по умолчанию**)
- Менять статус кандидата (write: `PATCH /candidates/{id}/stage`)

**Вывод:** решение может быть на read-only (показать рекомендации, кому отправить отказ), но без write и интеграции с мессенджерами/email не решит проблему полностью.

### Вопрос 3: Реалистично ли MVP за 2–3 недели?

**Условно, да.** MVP может быть:
1. Агент анализирует события в воронке
2. Идентифицирует кандидатов, которые не получили ответ >N дней
3. Выдает рекомендацию: "Отправить отказ", "Позвонить", "Переместить в резерв"
4. **Вариант без письма:** пишет шаблон отказа в комментарий (рекрутер копирует и отправляет вручную)

**Рисков**: нет собственного канала отправки (требуется внешняя интеграция). Решение = рекомендации + напоминания в системе.

### Вопрос 4: Можно ли показать на демо?

**Да.** Сценарий:
1. Воронка с 10–15 фейковыми кандидатами на разных этапах
2. Кандидаты без ответа >7 дней
3. Агент показывает: "3 кандидата требуют отказа", "1 кандидат заморозился после интервью"
4. Рекомендации с шаблонами отказов
5. На экране видна таблица: "Имя, Статус, Дни без ответа, Рекомендация"

---

### **Решаемость: 3** (данные в API есть, но нет собственного канала отправки уведомлений; решение = рекомендации в систему)

### **Демо-потенциал: 4** (понятны рекомендации, но нужно объяснять, что это не автоматическая рассылка)

## C04: Нанимающие менеджеры — медленный фидбек, смена требований (Балл: 2)

### Описание боли
Нанимающий менеджер не дает четкого фидбека по кандидатам. Требования размыты или меняются. Рекрутер застревает в ожидании решения менеджера.

### Вопрос 1: Есть ли нужные данные в API?

**Частично.** API позволяет:
- Видеть комментарии менеджера (если написал)
- Видеть смену статуса кандидата
- Видеть историю изменений требований вакансии (если доступна в `events_stream`)

**Endpoint-возможности:** `GET /events_stream`, `GET /vacancies/{id}`, но **нет встроенного функционала отслеживания фидбека менеджера или напоминания о просрочке**.

### Вопрос 2: Достаточно ли read-only?

**Да, read-only достаточно для рекомендаций.** Агент может:
- Отслеживать, сколько дней менеджер не дал фидбек (read: `GET /events_stream`)
- Выявить "зависшие" кандидатов (в статусе "на рассмотрении" >N дней)
- Рекомендовать: "Позвонить менеджеру", "Напомнить про кандидата X"
- **Опционально:** написать напоминание менеджеру в комментарий вакансии (write: `POST /vacancies/{id}/comments`)

### Вопрос 3: Реалистично ли MVP за 2–3 недели?

**Да, реалистично.** MVP = агент, который:
1. Получает список кандидатов по вакансии
2. Считает дни с последнего события (комментария, смены статуса)
3. Если >5 дней без фидбека → выдает алерт "Требуется фидбек от менеджера"
4. Показывает сводку: "1 кандидат ждет 8 дней", "Менеджер не ответил на 3 вакансиях"

**Сложность:** низкая. Простая логика на временных метриках.

### Вопрос 4: Можно ли показать на демо?

**Да, очень наглядно.** Сценарий:
1. Воронка с вакансиями и кандидатами на разных сроках ожидания
2. Агент показывает: "🔴 Кандидат A — 12 дней без фидбека", "🟡 Кандидат B — 5 дней"
3. Рекомендация: "Позвонить менеджеру о кандидате A"
4. На экране видна сводка: "Критичные задержки: 2, Требуют внимания: 3"

---

### **Решаемость: 4** (данные в API полностью, логика простая, но недостаточно для автоматического ускорения процесса; требуется ручное действие менеджера)

### **Демо-потенциал: 5** (красные флаги очень наглядны, понимается за 30 секунд)

## C06: База/ATS-гигиена — дубли кандидатов, устаревшие данные, кадровый резерв (Балл: 2)

### Описание боли
База засоряется дублями кандидатов (одно и то же резюме добавлено дважды). Контакты устаревают. Кадровый резерв хаотичен, поиск по базе невозможен (нет семантического поиска). Когда вакансия срочная, рекрутер не может быстро найти подходящего из резерва по навыкам.

### Вопрос 1: Есть ли нужные данные в API?

**Да.** API позволяет:
- Получить список всех кандидатов (потенциально в резерве)
- Прочитать карточку кандидата (ФИ, контакты, навыки, опыт, статус)
- Видеть, в каких вакансиях участвовал кандидат (история)
- Видеть дату последнего контакта (events_stream)

**Endpoint-возможности:** `GET /candidates`, `GET /candidates/{id}`, `GET /events_stream`.

### Вопрос 2: Достаточно ли read-only?

**Да и нет.** 
- **Для поиска дублей:** read-only достаточно. Сравнить email и телефон → найти дубли.
- **Для поиска по резерву:** read-only достаточно для простого поиска (ключевые слова в резюме, опыт), **но НЕ достаточно для семантического поиска** (что запрещено в API).
- **Для обновления резерва:** нужен write (добавить метку "резерв", обновить контакты).

### Вопрос 3: Реалистично ли MVP за 2–3 недели?

**Да.** MVP = агент, который:
1. Сканирует всех кандидатов по вакансии
2. **Поиск дублей:** находит кандидатов с одинаковыми email/телефон, уведомляет рекрутера
3. **Поиск из резерва:** ищет кандидатов по ключевым словам навыков (простой текстовый поиск, не ML)
4. **Актуальность:** показывает, когда последний контакт, помечает "холодные" контакты (>6 мес)
5. Выдает список: "Дубли для слияния (3)", "Подходящие из резерва (5)", "Холодные контакты (10)"

**Сложность:** низкая–средняя. Простой text matching по словам из вакансии и резюме.

### Вопрос 4: Можно ли показать на демо?

**Да, очень наглядно.** Сценарий:
1. Фейковая база из 50 кандидатов (резерв + отклоненные)
2. Новая вакансия "Python Senior" (ключевые слова: Python, 5+ лет, архитектура)
3. Агент находит: "2 дубля кандидата X", "5 подходящих из резерва", "15 холодных контактов"
4. На экране: таблица с кандидатами, статус, рекомендация, дата последнего контакта

---

### **Решаемость: 5** (все данные в read-only API, простая логика, демонстрирует ценность)

### **Демо-потенциал: 5** (наглядная таблица, понимается сразу)

---

## C01: Sourcing — поиск и привлечение кандидатов (Балл: 2)

### Описание боли
Рекрутер не может быстро найти подходящего кандидата из собственной базы. API не умеет семантический поиск. Приходится искать кандидата вручную (пролистывать профили) или по старым рассылкам. Конкуренция за топ-кандидатов высока.

### Вопрос 1: Есть ли нужные данные в API?

**Да, но с ограничениями.** API позволяет:
- Искать кандидатов по имени, email, телефон (точный поиск, **не семантический**)
- Получить резюме и карточку
- Видеть опыт, навыки в структурированном виде (если парсено)

**Endpoint-возможности:** `GET /candidates` с фильтром, но **нет встроенного семантического поиска**.

### Вопрос 2: Достаточно ли read-only?

**Да для простого sourcing.** Агент может:
- Получить список кандидатов по вакансии / из базы
- Фильтровать по ключевым словам (простой text matching)
- Выдать топ-N кандидатов для контакта
- **Но:** не может понять "похожие навыки", "скрытые компетенции" (требуется ML/embeddings — запрещено)

### Вопрос 3: Реалистично ли MVP за 2–3 недели?

**Да.** MVP = агент, который:
1. При новой вакансии ищет в базе кандидатов по ключевым словам
2. Выявляет "холодные" контакты, которые давно не контактировали
3. Ранжирует по: совпадение навыков, свежесть контакта, предыдущие интервью
4. Рекомендует: "Позвонить A (совпадение 80%, последний контакт месяц назад)"

**Сложность:** низкая. Поиск по ключевым словам + простая ранжировка.

### Вопрос 4: Можно ли показать на демо?

**Да.** Сценарий:
1. Вакансия "Python Developer, 3+ лет"
2. Агент ищет в базе 100 кандидатов
3. Выдает: "Топ-5 кандидатов для повторного контакта"
4. На экране: таблица с именами, опытом, скором совпадения, последним контактом

---

### **Решаемость: 4** (данные есть, но поиск ограничен точным matching; семантический поиск запрещен; решение работает для базовых случаев)

### **Демо-потенциал: 4** (понимается, но нужно объяснять, что это не ML-поиск)

## C08: Массовый найм и большие объёмы (Балл: 2)

### Описание боли
При найме 30–40 человек одновременно рекрутер не успевает обрабатывать отклики, назначать интервью, отправлять уведомления. 51% рекрутеров раздражены, что кандидаты не приходят на интервью или не выходят в первый день.

### Вопрос 1: Есть ли нужные данные в API?

**Да.** API позволяет:
- Получить список откликов по вакансии
- Видеть этапы кандидатов в воронке
- Писать комментарии, менять статусы
- Получать причины отказов
- Видеть календарь интервью

**Endpoint-возможности:** `GET /candidates`, `GET /vacancies/{id}`, `GET /events_stream`, `PATCH /candidates/{id}/stage`, `POST /candidates/{id}/comments`.

### Вопрос 2: Достаточно ли read-only?

**Нет, нужен write-back.** Требуется:
- Массово менять статусы кандидатов (write)
- Писать автоматические приглашения на интервью (требуется вебхуки или внешняя интеграция)
- Отправлять напоминания перед интервью (требуется интеграция)

**Решение:** можно на read-only дать рекомендации (кого пригласить, кого отклонить), но без write и интеграции не решит проблему полностью.

### Вопрос 3: Реалистично ли MVP за 2–3 недели?

**Условно, да.** MVP = агент, который:
1. Получает список откликов на вакансию (при массовом найме)
2. Быстро отсеивает явно неподходящих (по ключевым словам)
3. Предлагает автоматический график интервью (на основе доступных временных слотов)
4. Выдает рекомендацию: "Пригласить 25 кандидатов, отклонить 150"
5. Пишет комментарии "Приглашение на интервью (автогенерировано)" для копирования

**Рисков:** без вебхуков решение требует ручного действия рекрутера.

### Вопрос 4: Можно ли показать на демо?

**Да.** Сценарий:
1. Вакансия с 500 откликами
2. Агент обрабатывает и выдает: "Приглашить 30 (по релевантности)", "Отклонить 400", "В очередь 70"
3. Предлагает расписание интервью: "День 1: 8 интервью, День 2: 7, ..."
4. На экране: сводка "Обработано 500, Рекомендация готова за 3 сек"

---

### **Решаемость: 4** (данные есть, логика простая, но без вебхуков требует ручного действия; также требуется интеграция для отправки приглашений)

### **Демо-потенциал: 4** (понимается сводка, но нужно объяснять, что это рекомендации)
