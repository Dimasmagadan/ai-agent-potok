# Брейншторм идей для конкурса — сессия GPT, 2026-08-18

Статус: **исследование и приоритизация, финальная идея ещё не выбрана**.

Этот файл продолжает [`BRAINSTORM.md`](BRAINSTORM.md) и [`BRAINSTORM-GLM.md`](BRAINSTORM-GLM.md). Здесь идеи сопоставлены с реальными возможностями API «Потока», личными задачами Дмитрия и уже реализованными проектами.

## Краткий вывод

Самый сильный вариант для Дмитрия — не обычный проверяльщик резюме, а **Hiring Debt Radar / Аудитор рекрутингового процесса**.

Он объединяет уже существующие активы:

- «Нюхослав»: `источник → правило риска → алерт → повторная проверка`;
- Bitrix-анализ: классификация событий, задержек и повторяющейся ручной работы;
- Meeting Debt Ledger: поиск незакрытых действий после встреч;
- `meet`: дополнительное создание доказательного фидбека после интервью;
- API «Потока»: вакансии, кандидаты, этапы, события, календарь и комментарии.

Агент:

1. Находит кандидатов, слишком долго находящихся на этапе.
2. Находит завершённые интервью без содержательного фидбека.
3. Показывает кандидатов без следующего действия или ответственного.
4. Группирует причины отказов и узкие места воронки.
5. Отправляет рекрутеру короткие алерты и недельный отчёт.
6. Опционально принимает транскрипт из `meet` и готовит черновик фидбека.
7. Записывает результат в «Поток» только после подтверждения человеком.

Это оригинальнее простого Funnel SLA Watchdog, безопаснее автоматического скоринга кандидатов и лучше соответствует карьерному направлению Дмитрия `AI Workflow / Automation Engineer`.

## Что на самом деле даёт API «Потока»

API «Потока» не содержит собственного AI-анализа. Это API рекрутинговой системы, которое даёт внешнему агенту данные, триггеры и канал возврата результата.

Через API можно:

- читать, создавать и обновлять вакансии;
- читать, искать, создавать и обновлять кандидатов;
- получать резюме и карточку кандидата;
- добавлять кандидата на вакансию;
- видеть и менять этап воронки;
- читать комментарии, звонки, встречи, задачи и системные события;
- синхронизировать события через `events_stream`;
- создавать комментарии в карточке кандидата;
- прикреплять документы и отчёты;
- работать с интервью и напоминаниями в календаре;
- получать причины отказов, пользователей и справочники;
- получать заявки на подбор и штатное расписание, если модуль подключён;
- принимать вебхуки о событиях, если их настроила команда «Потока»;
- показывать вакансии и принимать отклики через публичный Career API.

Каноническая интеграция выглядит так:

```text
кандидат дошёл до этапа
→ вебхук или polling
→ внешний агент получает кандидата и вакансию
→ выполняет анализ
→ показывает статус обработки
→ возвращает комментарий, документ или обновлённые поля
```

### Важные ограничения

- Внешний API требует Bearer-токен компании.
- Career API без токена даёт только опубликованные вакансии и форму отклика, а не базу кандидатов.
- Вебхуки нельзя самостоятельно включить через API: их настраивает команда «Потока».
- Лимит — 100 запросов за 10 секунд на токен.
- В API есть персональные данные кандидатов; нельзя бездумно отправлять резюме и транскрипты во внешние LLM.
- API не проверяет качество резюме, не извлекает навыки и не принимает AI-решение о найме.
- Автоматический отказ или перемещение кандидата должны быть исключены из первого MVP.
- Для воспроизводимости конкурсному проекту нужны обезличенные fixtures и demo-режим без реального tenant.

## Какие проблемы Дмитрия может закрыть проект

### 1. Нет публичного доказательного кейса

У Дмитрия уже есть опыт построения интеграций, мониторинга и аналитических pipeline, но не хватает публичного артефакта, который показывает полный цикл:

```text
предметная проблема
→ discovery с экспертом
→ интеграция с отраслевым API
→ AI/data pipeline
→ измеримый результат
→ воспроизводимый open-source проект
```

Конкурс снимает часть обычных ограничений: разрешает open source и даёт внешний контур видимости через демодень и витрину решений.

### 2. Нужен кейс под Skill Combo

Сильный Skill Combo здесь:

> Senior developer + AI automation + API integration + process analytics + работа с предметником-рекрутером.

Это подходит сразу под несколько направлений:

- AI Workflow / Automation Engineer;
- бизнес- или системный аналитик;
- Solutions / Pre-sales Engineer;
- руководитель цифровизации;
- интегратор n8n/Make и корпоративных API.

### 3. Есть много движков, но мало подтверждённых outcomes

Проект позволяет собрать в одном кейсе уже существующие паттерны, а не начинать ещё один большой side-project с нуля.

### 4. Не хватает знания чужого домена

Разговор со знакомым рекрутером превращает конкурс из технической фантазии в domain-capture эксперимент. Главная ценность разговора — не выбрать фичу, а получить конкретный повторяющийся процесс, пример последнего случая и критерий полезности.

## Главная идея: Hiring Debt Radar

### Проблема

В рекрутинге накапливается операционный долг:

- кандидат завис на этапе;
- после интервью нет фидбека;
- не назначено следующее действие;
- рекрутер или нанимающий менеджер не отвечает;
- причина отказа не заполнена или слишком общая;
- одна и та же ручная операция повторяется по каждой вакансии;
- руководство узнаёт о проблеме только после срыва срока закрытия.

### Решение

Read-only агент регулярно анализирует вакансии, кандидатов и события, формирует список исключений и объясняет, почему каждый случай требует внимания.

Примеры сигналов:

- `Кандидат 8 дней на screening, SLA вакансии — 3 дня`;
- `Интервью завершилось 26 часов назад, фидбек отсутствует`;
- `После комментария «вернуться завтра» прошло 4 дня, следующего события нет`;
- `У вакансии 14 активных кандидатов, но движения по этапам не было 7 дней`;
- `За месяц 32% отказов отмечены общей причиной «не подходит»`;
- `У рекрутера 19 просроченных кандидатов против медианы отдела 4`.

### Выходы

- Telegram-алерт ответственному;
- ежедневный digest исключений;
- недельный отчёт по recruitment debt;
- комментарий в карточке кандидата после подтверждения;
- отчёт «какие три автоматизации дадут наибольший эффект»;
- локальный audit log действий агента.

### Почему это подходит Дмитрию

- Переиспользует архитектуру «Нюхослава».
- Переносит уже реализованный подход Bitrix task audit в новый домен.
- Развивает идею Meeting Debt Ledger.
- Даёт нейтральный публичный кейс AI Orchestrator.
- Не требует обучать ML-модель.
- Не принимает рискованных решений о найме.
- Может быть перенесён на другие ATS, CRM и task trackers.

### Минимальный vertical slice

```text
Potok events_stream + AJS Joins
→ нормализованные события
→ три правила recruitment debt
→ persistent dedupe/cooldown
→ Telegram digest
→ ссылка на карточку в Потоке
```

Первые три правила:

1. Кандидат находится на этапе дольше порога.
2. После интервью нет комментария с фидбеком.
3. После последнего события нет следующего действия дольше порога.

### Второй этап

```text
транскрипт интервью
→ evidence-based draft
→ preview и редактирование рекрутером
→ POST комментария в Поток
→ отдельное предложение следующего этапа
```

## Проверка качества резюме

### Короткий ответ

Да, с помощью API «Потока» можно построить сервис проверки резюме, но анализ делает внешний сервис, а не API.

«Поток» предоставляет:

- резюме и карточку кандидата;
- требования вакансии;
- этап и историю взаимодействий;
- место, куда вернуть отчёт.

Внешний агент выполняет:

- извлечение опыта и навыков;
- проверку полноты и структуры;
- сопоставление с вакансией;
- поиск неподтверждённых требований;
- подготовку вопросов для скрининга;
- формирование объяснимого отчёта.

### Что лучше делать

Не универсальный `Resume Quality Checker`, а **Screening Matcher**:

```text
кандидат + конкретная вакансия
→ совпадения
→ пробелы
→ подтверждающие фрагменты
→ вопросы рекрутеру
→ решение принимает человек
```

### Что нельзя обещать

- доказать правдивость резюме;
- объективно измерить «качество человека»;
- автоматически решить, кого нанять;
- безопасно отказать кандидату без участия человека;
- исключить дискриминацию одним prompt;
- проверить дипломы и работодателей без внешних источников.

### Доказательный Skill Combo Offer

Проверка резюме может быть одной фичей, но более сильный сервисный оффер:

> Подключаем ATS в read-only режиме, находим задержки, потерянный фидбек и повторяющуюся ручную работу, затем выдаём карту узких мест и три приоритетные автоматизации.

Вход:

- read-only API token или обезличенная выгрузка;
- период анализа;
- список этапов и SLA;
- короткое интервью с рекрутером.

Выход:

- cycle time по этапам;
- кандидаты и вакансии с операционным долгом;
- повторяющиеся действия;
- причины задержек и отказов;
- automation roadmap;
- расчёт потенциально сэкономленного времени.

Такой оффер переносится на Bitrix, amoCRM и другие процессные системы.

## Применение существующих проектов

### Нюхослав → Hiring Debt Radar / Candidate Radar

Архитектура переносится естественно:

```text
AIS + погода           → Potok API + events_stream
риск запаха            → риск задержки или потери кандидата
Telegram-алерт         → алерт рекрутеру
подтверждение запаха   → feedback рекрутера
recovery check         → проверка, закрыт ли recruitment debt
```

Что можно переиспользовать концептуально:

- polling и scheduler;
- нормализацию входных данных;
- dedupe;
- threshold/risk rules;
- cooldown;
- Telegram-карточки и inline-действия;
- хранение истории алертов;
- Docker/FastAPI/PostgreSQL-контур.

Необходимо добавить:

- API client с Bearer auth;
- pagination и backoff для `429`;
- persistent cursor;
- outbox/retry для уведомлений;
- модель вакансии, кандидата и AJS Join;
- privacy-safe представление кандидата.

### meet → Interview Copilot

Естественный сценарий:

```text
выбор кандидата и вакансии
→ запись интервью
→ локальная транскрипция и диаризация
→ компетенции, риски и вопросы без ответа
→ цитаты с timestamps
→ preview и редактирование
→ комментарий в карточку кандидата
```

Чтобы сохранить воспроизводимость, обязательным входом должен быть обычный текстовый транскрипт. Локальная запись и Whisper остаются дополнительной возможностью.

Безопасные правила:

- raw audio не отправляется в «Поток»;
- полный транскрипт не отправляется по умолчанию;
- voice embeddings не экспортируются;
- участники уведомляются о записи;
- результат содержит evidence, а не только AI-вердикт;
- отправка выполняется после preview;
- смена этапа подтверждается отдельно.

### intercom → Recruiter Pulse

Сам домофон к HR не относится. Полезны отдельные продуктовые и технические паттерны:

- компактный tray-интерфейс;
- loading/success/error state;
- защита от повторного действия;
- API-вызовы вне UI;
- безопасные одношаговые действия;
- переход из уведомления в основную систему.

Возможный результат — menubar inbox:

```text
3 события требуют внимания

Анна: нет фидбека после интервью
[Открыть в Потоке] [Создать черновик]

Иван: 6 дней на screening
[Открыть] [Напомнить]
```

Не следует переносить `intercom` целиком: event monitor, audit log и надёжный persisted dedupe придётся строить заново.

### holotek → правила переходов и cooldown

CO₂-датчик доменно не связан с наймом, но полезна модель состояния:

```text
normal → warning → critical → recovered
```

Для «Потока»:

```text
fresh → approaching SLA → overdue → resolved
```

Полезные правила:

- первый снимок создаёт baseline без лишнего алерта;
- ухудшение вызывает немедленное уведомление;
- одинаковое состояние не создаёт повторы;
- разрешение проблемы создаёт recovery event;
- новый алерт возможен после cooldown или изменения evidence.

## Другие сильные идеи

### 1. Interview Feedback Debt

Узкая версия Hiring Debt Radar: агент проверяет, появился ли содержательный фидбек после интервью, и предлагает доказательный черновик.

Плюсы:

- очень понятная боль;
- естественная связка с `meet`;
- легко показать на демо;
- результат остаётся в карточке кандидата.

### 2. Recruiter Activity Audit

Применить к `events_stream` уже существующий метод Bitrix-анализа:

- классифицировать действия;
- измерить cycle time;
- найти rework и повторные переходы;
- найти ручные операции;
- выдать рейтинг автоматизаций.

Это один из лучших вариантов для доказательства роли AI Orchestrator.

### 3. Demand-vs-Reality Tracker

Сравнивать заявку «нанять N человек к дате» с фактической скоростью воронки и числом финалистов.

Сильная идея, но зависит от доступности модуля Staffing в песочнице.

### 4. Career Site SEO/GEO Auditor

Анализировать публичные вакансии и карьерный сайт:

- ясность текста;
- метаданные;
- Schema.org;
- индексируемость;
- passage-level citability;
- доступность AI-краулерам;
- дубли и слабые шаблоны вакансий.

Это сильный личный SEO/GEO-кейс, но для конкурса API используется менее глубоко.

### 5. Candidate Radar

Новые или обновлённые кандидаты проходят объяснимые hard gates и fit-score, после чего рекрутер получает только важные карточки.

Риски:

- идея менее оригинальна;
- scoring может создавать ложную объективность;
- необходимо исключить чувствительные признаки;
- решение должно оставаться за человеком.

### 6. Recruiter Telegram Copilot

Natural-language интерфейс над API:

- «Кто завис?»;
- «Где нет фидбека?»;
- «Какие интервью сегодня?»;
- «Какие вакансии без движения?».

Опасные действия доступны только после явного подтверждения.

## Текст для разговора с рекрутером

### Что умеет API «Потока» простым языком

> API «Потока» позволяет программе читать вакансии и кандидатов, видеть этапы найма, историю действий, интервью и причины отказов. Через него можно находить зависших кандидатов, готовить отчёты, проверять наличие фидбека, анализировать резюме, создавать напоминания и возвращать результаты внешнего AI-сервиса прямо в карточку кандидата. Решения при этом может подтверждать рекрутер.

### Вопросы рекрутеру

1. Что после интервью приходится делать вручную?
2. Как вы замечаете, что кандидат завис на этапе?
3. Где чаще всего теряется фидбек?
4. Какие регулярные отчёты отнимают больше всего времени?
5. Какие данные приходится переносить между ATS, таблицами и мессенджерами?
6. Какие причины отказов хотелось бы анализировать?
7. Что чаще всего забывают рекрутеры или нанимающие менеджеры?
8. Какую одну задачу вы первой отдали бы надёжному помощнику?
9. Как вы поймёте, что такой помощник действительно полезен?

### Как проводить разговор

Не спрашивать только «нужна ли вам такая функция». Просить конкретные случаи:

- «Когда это произошло в последний раз?»
- «Покажите, как вы это делаете сейчас».
- «Сколько раз это происходит за неделю?»
- «Что случается, если это не сделать?»
- «Кто ещё участвует?»
- «Где хранится результат?»
- «Как руководство узнаёт о проблеме?»

Сильный сигнал — процесс частый, ручной, проходит через несколько систем и уже имеет цену ошибки или задержки.

## Перепрофилирование API внутри HR

Наиболее естественное направление — **People Workflow API**.

Модель:

```text
Applicant → человек
Job       → программа или процесс
Stage     → этап процесса
AJS Join  → участие человека в процессе
```

### Онбординг 30-60-90

- `Job` = программа адаптации;
- `Applicant` = новый сотрудник;
- `Stage` = чекпоинт;
- агент напоминает, собирает обратную связь и готовит отчёт.

### Performance Review

- `Job` = цикл оценки;
- этапы = самооценка, руководитель, калибровка, фидбек;
- агент контролирует сроки и полноту evidence.

### Обучение и наставничество

- `Job` = программа или когорта;
- `Applicant` = участник;
- этапы = модули и контрольные точки.

### Внутренняя мобильность

Это самый естественный вариант: внутренний сотрудник остаётся кандидатом на реальную внутреннюю вакансию, а агент объясняет skill gaps и возможный план развития.

Эти сценарии соответствуют конкурсу и не требуют полностью ломать доменную модель.

## Если полностью отказаться от HR

Полностью вне кадров текущий API использовать невыгодно. Это не generic workflow engine: сущности, поля и интерфейс остаются рекрутинговыми.

Технически можно переименовать сущности:

- кандидат → участник конкурса;
- вакансия → конкурс или акселератор;
- этап → проверка заявки, жюри, финал;
- кандидат → абитуриент;
- вакансия → образовательная программа;
- кандидат → клиент;
- вакансия → программа onboarding;
- кандидат → подрядчик;
- вакансия → процедура допуска.

Возможные самостоятельные рынки:

- конкурсные заявки;
- поступление на образовательные программы;
- акселераторы и гранты;
- onboarding клиентов;
- квалификация партнёров;
- согласование подрядчиков;
- обработка заявок граждан;
- generic case management.

Но для этого «Потоку» нужно выделить отдельный продуктовый слой:

```text
Person / Entity
→ Program / Process
→ Stage
→ Event
→ Document
→ Decision
```

Это может быть предложением компании создать **Workflow/Applications API**, но как конкурсная заявка такой сценарий слабее: реальный пользователь не станет покупать рекрутинговую ATS ради фейковых вакансий и кандидатов.

## Архитектура рекомендуемого MVP

```text
Potok API
  ├── Jobs
  ├── AJS Joins
  ├── Events / events_stream
  ├── Calendar
  └── Users
         │
         ▼
Potok adapter
  ├── Bearer auth
  ├── pagination/cursor
  ├── retry/backoff
  └── normalized DTO
         │
         ▼
Debt detector
  ├── stale stage
  ├── missing interview feedback
  ├── missing next action
  └── vacancy inactivity
         │
         ▼
Persistent state
  ├── cursor
  ├── dedupe key
  ├── cooldown
  ├── alert state
  └── audit log
         │
         ▼
Delivery
  ├── Telegram
  ├── daily/weekly digest
  └── human-approved Potok comment
```

### Режимы

`read-only` по умолчанию:

- читает данные;
- формирует алерты;
- ничего не меняет в «Потоке».

`write-back` после явного включения:

- создаёт комментарий;
- прикрепляет отчёт;
- не двигает кандидата автоматически;
- ведёт audit log;
- проверяет, что состояние не изменилось после построения рекомендации.

### Воспроизводимый demo

- обезличенные JSON fixtures;
- mock Potok server;
- заранее заданные SLA;
- три демонстрационных нарушения;
- Telegram preview или локальная HTML-страница;
- golden output для тестов;
- опциональный настоящий API smoke test.

## Риски и ограничения

### Privacy

- минимизировать получаемые поля;
- не сохранять raw резюме без необходимости;
- не отправлять полные карточки в Telegram;
- не включать реальные sandbox payloads в open-source репозиторий;
- использовать обезличенные fixtures;
- задать retention policy;
- отдельно логировать, что именно отправлено в «Поток».

### Hiring bias

- не использовать возраст, пол, фото, семейное положение и другие чувствительные признаки;
- показывать evidence;
- версионировать правила и prompts;
- не называть score объективной оценкой человека;
- не выполнять автоматический отказ.

### Надёжность

- учитывать `429` и `Retry-After`;
- делать polling инкрементальным;
- дедуплицировать события и уведомления;
- обрабатывать повторные вебхуки;
- хранить состояние в БД, а не только в памяти;
- разделять получение события и тяжёлую обработку;
- считать timeout write-запроса неопределённым результатом, а не сразу повторять действие.

### Конкурсные риски

- уточнить, какие модули включены в песочнице;
- проверить доступность Calendar, Staffing, workflows и resume URL;
- уточнить порядок настройки вебхуков;
- не строить MVP только на модуле, который может отсутствовать;
- подтвердить требования к open source и допустимость публикации API-материалов.

## Следующие проверки

1. Провести problem interview со знакомым рекрутером.
2. Получить доступ к sandbox и проверить реальные payloads.
3. Проверить, есть ли надёжная дата входа на текущий этап.
4. Проверить, как связаны календарное интервью и последующий комментарий.
5. Проверить incremental-семантику `events_stream` и сохранение курсора.
6. Уточнить наличие Staffing и workflow в конкурсной песочнице.
7. Выбрать один основной сигнал с понятной ценой задержки.
8. Собрать read-only vertical slice до добавления LLM и write-back.
9. Получить от рекрутера оценку полезности результата.
10. Только после этого расширять агент до Interview Copilot или Activity Audit.

## Рекомендуемый порядок выбора

Если нужна самая надёжная конкурсная заявка:

> Hiring Debt Radar с тремя правилами и Telegram/digest.

Если важнее оригинальность и демонстрация существующего `meet`:

> Interview Copilot с текстовым входом, evidence и human-approved export.

Если важнее карьерный кейс AI Orchestrator:

> Recruiter Activity Audit с отчётом об узких местах и automation roadmap.

Наиболее сильная комбинация:

> Hiring Debt Radar как основной воспроизводимый продукт + Interview Copilot как опциональный модуль для закрытия отсутствующего фидбека.

## Текущий статус

Финальная идея не выбрана. Основная рабочая гипотеза — **Hiring Debt Radar**, дополненный опциональным **Interview Copilot**. Следующий шаг — проверить гипотезу на конкретных последних случаях знакомого рекрутера и сопоставить их с реальными данными конкурсной песочницы.
