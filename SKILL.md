# Поиск по кадровому резерву «Потока» + дедупликация + доп. сценарии

Read-only скилл поверх открытого API «Потока» (см. `docs/`, `docs/tools.json`).
Дизайн зафиксирован в [`SDD-C06-TALENT-POOL.md`](SDD-C06-TALENT-POOL.md) (резерв/
поиск/дедуп), [`SDD-C07-REOPEN-CANDIDATES.md`](SDD-C07-REOPEN-CANDIDATES.md)
(пересмотр прошлых кандидатов), [`SDD-C08-DELIVERY-EXTENSIONS.md`](SDD-C08-DELIVERY-EXTENSIONS.md)
(полнотекст резюме, режим соискателя, каналы доставки) и
[`SDD-C09-INTERNAL-MOBILITY.md`](SDD-C09-INTERNAL-MOBILITY.md) (внутренний бот
для сотрудников поверх того же `job_seeker.py`) — не пересматривать архитектуру
без явной причины, там уже разобраны альтернативы.

Реализация функций доступа к данным и ранжирования — `scripts/talent_pool.py`
(stdlib only, без сторонних зависимостей). Запускать через Bash. Матчинг и
сортировка внутри скрипта детерминированные — LLM отвечает только за
нормализацию/расширение запроса синонимами, не за ранжирование.

## Настройка окружения

Скрипт читает `POTOK_BASE_URL` и `POTOK_API_TOKEN` из окружения. Либо
реальный тенант (см. README «Подключение»), либо демо-режим:

```bash
python3 scripts/mock_server.py &            # поднимает mock API на :8765 из fixtures/
export POTOK_BASE_URL=http://localhost:8765
export POTOK_API_TOKEN=demo
```

## Сценарий 1: «найди кандидатов в резерве под запрос X»

1. Извлеки из запроса рекрутера ключевые термы (роль, навыки, отраслевые
   термины, грейд, локация, формат работы). Расширяй их синонимами и вариантами
   написания в контексте сферы вакансии, а не только IT: «питон»→python,
   «джун»→junior; «хантер»→b2b sales/business development; «медсестра»→
   сестринское дело; «кассир»→продавец-кассир. Помечай каждый терм как
   `original` (то, что буквально сказал рекрутер) или `synonym` (то, что
   добавила LLM) — это нужно для evidence.
2. Построй резерв и сохрани во временный файл:
   ```bash
   python3 scripts/talent_pool.py reserve > /tmp/reserve.json
   ```
3. Запусти поиск с термами в виде JSON-массива `[{"term": "...", "kind": "original"|"synonym"}, ...]`:
   ```bash
   python3 scripts/talent_pool.py search '<TERMS_JSON>' --reserve-file /tmp/reserve.json --top 10
   ```
4. Ответь рекрутеру таблицей: имя, id/ссылка на карточку (`{POTOK_BASE_URL}/applicants/{id}`
   на реальном тенанте), совпавшие термы отдельно по `matched_original` и
   `matched_synonym` (evidence). Если результатов нет — так и скажи, не
   выдумывай кандидатов.

Если рекрутёр явно просит «поискать по резюме» / «по тексту резюме» —
сначала прогони полнотекстовую индексацию, затем поиск с ней:

```bash
python3 scripts/talent_pool.py cv-index --reserve-file /tmp/reserve.json --cache-dir .cv_cache
python3 scripts/talent_pool.py search '<TERMS_JSON>' --reserve-file /tmp/reserve.json --cv-cache-dir .cv_cache --top 10
```

В ответе обязательно упомяни `summary.cv_coverage` (`with_cv_text`/`without`) —
честно сообщи, для какой доли кандидатов резюме реально было проиндексировано.
Кандидатов, найденных только по резюме, помечай отдельно (evidence с
`"source": "cv"` и цитатой) — это не то же самое, что совпадение в title/tags.

## Сценарий 2: «покажи дубли кандидатов в базе»

```bash
python3 scripts/talent_pool.py dedup
```

Выведи список групп (`match`: phone/email, `value`, `applicant_ids`) —
таблицей или списком, с указанием, что делать дальше: рекрутер открывает
карточку в Потоке и жмёт «слить» сам (write-back в скилле отсутствует).

## Сценарий 3: «какие вакансии компании мне подходят» (соискатель/сотрудник)

Read-only, только открытый Career API — токен не нужен и не используется.

1. Извлеки из свободного текста кандидата профиль по формату
   [`SDD-C08-DELIVERY-EXTENSIONS.md`](SDD-C08-DELIVERY-EXTENSIONS.md) §6.2:
   `terms` (та же логика original/synonym, что в Сценарии 1) и `filters`
   (`city`, `schedule`, `salary_from` — только явно упомянутое). Покажи
   пользователю распознанные термы/фильтры **до** запуска — дай уточнить,
   если что-то не так.
2. Запусти подбор:
   ```bash
   python3 scripts/job_seeker.py jobs-match '<PROFILE_JSON>' --top 10
   ```
3. Ответь таблицей: название, `apply_url`, evidence. Явно скажи, что скилл не
   отправляет отклик — только показывает ссылку на страницу вакансии, где
   кандидат откликается сам. Текст кандидата никуда, кроме этого запроса,
   не передаётся: наружу уходят только GET-запросы списка вакансий.

## Сценарий 4: «сотрудник спрашивает про внутренние вакансии» (C09, внутренний бот)

Только для закрытой рассылки внутри компании — не публичный сценарий 3.
Авторизованный источник вакансий компании (`--fallback-v3`), включая
неопубликованные на карьерном сайте; конфиденциальные (`private: true`)
исключены, если явно не включены (`JOB_SEEKER_INCLUDE_PRIVATE=1`). Полный
контракт — [`SDD-C09-INTERNAL-MOBILITY.md`](SDD-C09-INTERNAL-MOBILITY.md) §3-4.

1. Извлеки профиль (та же логика, что в Сценарии 3) и покажи распознанное
   пользователю до запуска.
2. Если сотрудник спрашивает «какие вакансии мне подходят» — запусти:
   ```bash
   python3 scripts/job_seeker.py jobs-match '<PROFILE_JSON>' --fallback-v3 --internal --top 10
   ```
3. Если сотрудник спрашивает «чего мне не хватает для вакансии N» — запусти:
   ```bash
   python3 scripts/job_seeker.py jobs-gaps '<PROFILE_JSON>' --job-id N --fallback-v3 --internal
   ```
   Формулируй пробелы нейтрально («вакансия ожидает опыт от 3 лет»), не
   «вы не подходите» — та же тональность, что в Сценарии 4 SDD-C07. Поля из
   `unknown_fields` — не пробел, а недостаток данных с одной из сторон; так и
   объясняй пользователю, не выдавай их за несовпадение.

## Сценарий 5: «рекрутёр изменил условия вакансии, кого из отказов пересмотреть»

Отдельный, полностью специфицированный сценарий —
см. [`SDD-C07-REOPEN-CANDIDATES.md`](SDD-C07-REOPEN-CANDIDATES.md) §8 (команда
`talent_pool.py reopen`, формат `REQUEST_JSON`, машинный контракт результата).
Если рекрутёр назвал вакансию по имени, а не по ID — сначала запусти
`talent_pool.py jobs-find '<строка>'` (MCP: `potok_jobs_find`), покажи
совпадения (включая архивные — они часто и есть нужный `source_job_id`) и
дай рекрутёру выбрать; не подставляй ID по совпадению названия сам. Нет
совпадений — попробуй более широкий/другой по языку терм (напр.
«developer» вместо «разработчик»), матчинг по названию не знает синонимов.
Перед запуском обязательно уточни у рекрутёра прежние условия (или
референсную вакансию, чьи текущие условия считать прежними) — без этого
скилл не имеет права утверждать, что условия «изменились». Отдельно уточни,
откуда брать пул прошлых отказников (`source_job_id`): это та же карточка
вакансии (`use_target_as_source:true`) или отдельная, в т.ч. архивная,
вакансия под другим ID — не подставляй `use_target_as_source` по умолчанию
только потому, что рекрутёр назвал один ID. Если результат пустой
(`candidate_ids_observed: 0`) при `use_target_as_source:true`, прежде чем
сообщать «отказников нет», спроси, не велась ли история отказов под другим
ID вакансии.

## Обязательное правило: не пересказывай своими словами

Числа (`summary`, `cv_coverage`, `candidate_ids_observed` и т.п.) и коды
`warnings`/ошибок бери дословно из последнего вывода инструмента этого же
хода, а не из памяти или предположений. Если причина пустого/неожиданного
результата не следует явно из вывода инструмента — так и скажи («причина не
видна из ответа, нужно уточнить X»), не изобретай правдоподобные гипотезы
вместо прямой цитаты `warnings`.

## Ограничения (проговаривать явно, не скрывать)

- Матчинг по title/tags/резюме — детерминированный, без семантического
  поиска/embeddings; резюме индексируется только по явному запросу и только
  `.docx`/`.txt` полноценно (`.pdf` — если установлен `pdfminer.six`,
  `.doc`/`.rtf` не поддерживаются).
- Дедуп — точное совпадение нормализованного телефона/email, без
  fuzzy-логики по ФИО (Иван/Ваня, опечатки).
- Резерв не фильтруется по причине отказа — туда попадают и реально
  непригодные отклонённые кандидаты.
- Режим соискателя (Сценарий 3, публичный) показывает только опубликованные
  на карьерном сайте вакансии и никогда не отправляет отклик — только ссылку
  `apply_url`. Внутренний режим (Сценарий 4, `--fallback-v3`) — только для
  закрытой рассылки сотрудникам, никогда не для внешней аудитории.
- `city` в `--fallback-v3` не резолвится в имя (нет подтверждённого
  discovery-источника на 2026-09-03, см. SDD-C09 §2 п.3) — вакансии всегда
  дают `filter_unknown`/`unknown_fields` по городу в этом режиме, а не тихое
  несовпадение.
- Никакой записи в Поток нигде (никаких POST/PUT/PATCH), ни в одном канале
  доставки (SKILL/MCP/Telegram-бот).

Полный список — README.md, §5 SDD-C06, §9/§11 SDD-C07, §15 SDD-C08.
