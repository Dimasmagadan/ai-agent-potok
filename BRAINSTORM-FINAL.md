# Финальный брейншторм — конкурс AI-агентов «Потока»

Дата: 2026-08-18. Синтез трёх сессий: [`BRAINSTORM.md`](BRAINSTORM.md), [`BRAINSTORM-GPT.md`](BRAINSTORM-GPT.md), [`BRAINSTORM-GLM.md`](BRAINSTORM-GLM.md).

**Назначение файла:** единая точка входа для следующего шага — выбрать 1–2 идеи и написать SDD-план. Всё, что ниже, — отфильтрованный консенсус, а не полный протокол (полные каталоги и рассуждения остаются в исходных файлах).

## 1. Жёсткие рамки

- Конкурс «Потока» (events.potok.io/ai_agent_hr_contest), дедлайн **6 сентября 2026** — осталось ~2,5 недели. Идея должна быть узкой.
- Обязательно: open source (права у автора), HR-задача (критерий №1), воспроизводимость для проверяющих.
- API — рекрутинговая ATS: читает/пишет вакансии, кандидатов, этапы, события (`events_stream`), календарь, комментарии, документы, причины отказов; опционально Staffing/demands. AI-анализа в API нет — его делает внешний агент.
- Ограничения API: Bearer-токен компании, лимит 100 req/10 s, вебхуки включает только команда «Потока», в данных — ПДн кандидатов.
- Красные линии MVP: никакого автоматического отказа/перемещения кандидата, никаких чувствительных признаков (возраст, пол, фото), write-back только после подтверждения человеком.
- Для демо обязательны обезличенные fixtures + mock-сервер: проверяющий не имеет реального tenant.

## 2. Личный контекст (зачем участвовать)

- Карьерная рамка «AI Orchestrator»: домен → AI-пайплайн → видимый результат → владение доменом. SEO-кейс в Optimacros сработал технически, но публично не залогирован — это известная дыра.
- Конкурс закрывает два хронических блокера: снимает IP-конфликт (компания сама требует публикацию) и даёт бесплатный контур видимости (демо-день, витрина).
- Нужен публичный артефакт полного цикла: проблема → discovery с предметником → интеграция с отраслевым API → AI/data-пайплайн → измеримый результат → воспроизводимый open source.
- Есть знакомый рекрутер — problem interview возможно на этой неделе.

## 3. Куда сошлись все три сессии

Три независимых сессии дали одинаковую сходимость:

1. **Мониторинг операционного долга воронки** — самый безопасный и переиспользуемый паттерн (Нюхослав переносится почти один в один: поллер → правило риска → Telegram-алерт → recovery-check). Всплывал во всех трёх сессиях под именами Funnel SLA Watchdog → Hiring Debt Radar.
2. **Interview-направление (meet)** — самое оригинальное, но воспроизводимость лечится только универсальным текстовым входом (транскрипт как обязательный вход, локальный Whisper — опция).
3. **Vacancy/Career SEO** — сильнее как личный кейс под контент-опс/SEO-оффер, слабее как конкурсная заявка (API используется поверхностно).
4. Переобозначение сущностей (онбординг, performance review) — зафиксированный приём, но не проработан и рискует выглядеть натянуто.
5. Полный уход из HR — закрыт окончательно: противоречит условиям конкурса и критерию воспроизводимости.

## 4. Шорт-лист под SDD

### Финалист №1: Hiring Debt Radar (основная гипотеза)

Read-only агент находит операционный долг рекрутинга и объясняет каждый случай:

1. Кандидат на этапе дольше SLA.
2. Интервью завершилось — содержательного фидбека нет.
3. После последнего события нет следующего действия дольше порога.

Выходы: Telegram-алерт ответственному, ежедневный digest, недельный отчёт по recruitment debt, комментарий в карточку — только после подтверждения человеком.

Почему он:

- объединяет Funnel SLA Watchdog + Interview Feedback Debt + missing-next-action в один продукт — оригинальнее «просто watchdog», безопаснее скоринга кандидатов;
- максимально переиспользует готовое: архитектуру Нюхослава (поллер, dedupe, cooldown, Telegram, recovery), state-модель holotek (`fresh → approaching SLA → overdue → resolved`), метод Bitrix-аудита;
- лучшие оценки в обеих матрицах (польза 5, воспроизводимость 5, риск 2);
- vertical slice реалистичен в срок: `events_stream + AJS Joins → 3 правила → dedupe/cooldown → Telegram digest → ссылка на карточку`.

### Финалист №2 (опциональный модуль): Interview Copilot

Расширение Радара, а не отдельная заявка: `текстовый транскрипт → evidence-based черновик фидбека (цитаты с таймстампами) → preview рекрутером → POST комментария`. Закрывает ровно тот долг, который Радар обнаруживает (правило №2), демонстрирует meet, добавляет оригинальности демо. Локальная запись/Whisper — опция, не требование.

**Рекомендуемая комбинация (консенсус GPT-сессии, подтверждён здесь): Hiring Debt Radar как основной воспроизводимый продукт + Interview Copilot как модуль второй фазы.** SDD писать на Радар; Copilot — отдельным опциональным разделом с собственным cut-line.

### Запасной вариант: Recruiter Activity Audit

Если разговор с рекрутером покажет, что «долг» не болит, а болит «не понимаем, куда уходит время»: перенос Bitrix-метода (классификация событий, cycle time, rework, рейтинг автоматизаций) на `events_stream`. Те же оценки, что у Радара, лучший кейс роли AI Orchestrator, но результат — отчёт, а не живой агент, что слабее смотрится на демо-дне.

### Осознанно отложено (не удалено)

- **Vacancy SEO/Content Agent, Career Site SEO/GEO Auditor** — делать вне конкурса как личный SEO/контент-опс кейс; конкурсную заявку на них не строить.
- **Screening Matcher / Candidate Radar** — риск bias/ложной объективности (риск 4), много конкурентов.
- **Demand-vs-Reality Tracker** — сильная идея, но зависит от наличия Staffing-модуля в песочнице; вернуться, только если песочница его подтвердит и Радар окажется занят конкурентами.
- **Recruiter Telegram Copilot, Candidate Status Bot, остальной каталог GLM (25 идей)** — резерв; полный список в `BRAINSTORM-GLM.md`.

## 5. Архитектура MVP (для SDD)

```text
Potok API (Jobs, AJS Joins, events_stream, Calendar, Users)
  → Potok adapter (Bearer, pagination/cursor, retry/backoff на 429, normalized DTO)
  → Debt detector (stale stage / missing feedback / missing next action)
  → Persistent state (cursor, dedupe key, cooldown, alert state, audit log)
  → Delivery (Telegram, daily/weekly digest, human-approved comment)
```

Режимы: `read-only` по умолчанию; `write-back` — явное включение, только комментарий/документ, с проверкой, что состояние не изменилось после построения рекомендации.

Демо: обезличенные fixtures + mock Potok server + 3 заранее заложенных нарушения + golden output; настоящий API — опциональный smoke test.

## 6. Что проверить до SDD (гейты)

1. **Problem interview с рекрутером** — не «нужна ли фича», а конкретика: последний случай, частота в неделю, цена ошибки, где хранится результат. Вопросники готовы в `BRAINSTORM-GPT.md` и `BRAINSTORM-GLM.md` (взять любой, они эквивалентны).
2. **Песочница:** какие модули включены; есть ли надёжная дата входа на этап; как связаны календарное интервью и последующий комментарий; incremental-семантика `events_stream`; порядок настройки вебхуков (fallback — polling).
3. **Условия конкурса:** допустимость публикации API-материалов в open-source репо.

Гейт-решение: если рекрутер подтверждает боль «зависшие кандидаты / потерянный фидбек» → SDD на Hiring Debt Radar. Если нет — пересмотреть в пользу Recruiter Activity Audit.

## 7. Ключевые риски

- **Privacy:** минимизация полей, никаких полных карточек в Telegram, никаких реальных payloads в репо, retention policy, лог того, что отправлено в «Поток».
- **Bias:** нет чувствительных признаков, evidence вместо вердиктов, версионирование правил и prompts, никакого авто-отказа.
- **Надёжность:** 429/Retry-After, инкрементальный polling, persistent state в БД, timeout write-запроса = неопределённый результат (не слепой retry).
- **Конкурсные:** не строить MVP на модуле, которого может не быть в песочнице (Staffing, вебхуки); polling — обязательный fallback.

## 9. Апдейт 2026-08-18: problem interview проведено

Гейт №1 пройден. Рекрутер назвала две частые боли:

1. **Контроль прохождения испытательного срока.**
2. **Поиск по базе кадрового резерва** (по ключевым словам, подходящим навыкам).

Исходная формулировка «долг воронки найма» напрямую **не подтверждена** — зависших кандидатов и потерянный фидбек после интервью рекрутер не назвала. Но архитектура Радара выживает целиком: боль №1 — это тот же радар долгов, перенацеленный с воронки найма на воронку испытательного срока.

### Новый финалист №1: Probation Radar (контроль испытательного срока)

- Модель — приём «переобозначение AJS Join» из раздела 3, теперь обоснованный реальной болью: `Job` = программа испытательного срока, `Applicant` = новый сотрудник, `Stage` = чекпоинты (план ИС составлен → фидбек 1-го месяца → фидбек 2-го → решение → уведомление сотрудника).
- Правила — те же три, с доменной поправкой: чекпоинт просрочен; встреча по ИС прошла, а фидбек руководителя не зафиксирован; до конца ИС меньше N дней, а решения нет.
- Ключевой сигнал с юридической ценой ошибки: по ч. 1 ст. 71 ТК РФ о непрохождении ИС нужно письменно предупредить не позднее чем за 3 дня до конца срока; пропустил дедлайн — сотрудник прошёл ИС автоматически. Это ровно та «цена задержки», которую мы искали как критерий сильного сигнала.
- Конкурс: прямая категория (адаптация/онбординг); первая сессия уже зафиксировала, что поля ложатся почти без трения.
- Переиспользование: 100% архитектуры MVP из раздела 5 — меняются только имена правил и источник SLA (дата конца ИС из карточки).

### Финалист №2: Talent Pool Search (поиск по кадровому резерву)

- API даёт только точный поиск (имя/телефон/email) — семантику строим снаружи: выгрузка кандидатов и резюме → извлечение навыков (LLM) → локальный индекс (embeddings/FTS) → запрос на естественном языке → выдача с evidence-цитатами и ссылкой на карточку.
- Плюсы: настоящая AI-задача, зрелищное демо, боль реальна (резерв копится и лежит мёртвым).
- Минусы: резюме проходят через LLM/embeddings — privacy-контур строже (локальная модель или обезличивание); заметно больше нового кода; «AI-поиск по резюме» — предсказуемо популярная тема у конкурентов; для демо нужны синтетические резюме-fixtures.

### Решение по гейту

- **SDD писать на Probation Radar**: максимальное переиспользование, укладывается в срок, прямая категория конкурса, юридический SLA как убойный демо-сигнал.
- **Talent Pool Search** — второй кандидат: вернуться, если проверка песочницы (ниже) убьёт пост-найм воронку, либо как модуль второй фазы (не прошедшие ИС и отказанные финалисты → в резерв → поиск по нему).
- **Interview Copilot** отходит на третий план — боль фидбека после интервью рекрутер не назвала.

### Дополнительные проверки песочницы (к разделу 6)

1. Можно ли создать `Job` с произвольными этапами под программу ИС (или есть штатный модуль адаптации).
2. Как из API получить нанятых с датой выхода и датой конца ИС (finalists / поля карточки) — это источник SLA.
3. Уточнить у рекрутера: где ИС ведётся сейчас (в «Потоке», в Excel, нигде) и кто фиксирует фидбек руководителя — от этого зависит, откуда агент берёт факты.

## 10. Wildcard: «Тиндер для найма» (2026-08-18)

Шуточная/маркетинговая идея Дмитрия — оставлена на столе, как и все остальные.

Механика: кандидат добавляет анкету → она максимально обезличивается (ПДн, контакты, имена; работодатели обобщаются: «больница №3» → «медицинское учреждение»); навыки вытаскиваются через игру. Работодатели так же обезличенно добавляют вакансии. Обе стороны свайпают карточки друг друга (подходит/не подходит) в обе стороны.

Оценка:

- **Скрытый серьёзный компонент — обезличиватель резюме.** Пайплайн «резюме → LLM вычищает ПДн и обобщает работодателей, сохраняя сигнал о навыках» нужен и Talent Pool Search (privacy-контур перед LLM/embeddings), и демо-fixtures любой конкурсной идеи. Это общий модуль, ценный независимо от судьбы тиндера.
- **Практическая ценность выше, чем кажется:** взаимный свайп = match = раскрытие контактов по обоюдному согласию (double opt-in reveal, стандарт blind-hiring платформ). Обезличенность — фича против bias, согласуется с красными линиями раздела 7.
- **Интеграция с «Потоком»:** вакансии — из открытого Career API (уже публичны), match → создание отклика/кандидата через API. Для «Потока» это витринный канал привлечения — отсюда маркетинговый потенциал.
- **Слабости:** двусторонний cold start (без базы это демо, не продукт); это продукт с тяжёлым UI, а не агент — не в фокусе конкурса; аналоги существуют (Jobr, Switch, blind-hiring платформы); в 2,5 недели параллельно с основной заявкой не влезает.

Решение: в конкурс не выставлять. Два выхода: (а) «vision-слайд» в питче основной заявки, (б) обезличиватель резюме — выделить как переиспользуемый компонент и строить там, где он нужен всерьёз (Talent Pool Search, fixtures).
