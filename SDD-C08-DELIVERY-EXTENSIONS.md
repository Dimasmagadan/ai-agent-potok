# SDD: C08 - каналы доставки и расширения

Дата постановки: 2026-09-03. Заказчик: Дмитрий.

Документ объединяет три рабочих потока поверх готового C06 и спецификации C07:

- **Поток A** - полнотекстовый поиск по файлам резюме (снимает главное
  ограничение C06 «матчинг только по title/tags»).
- **Поток B** - режим соискателя: подбор вакансий компании под свободное
  описание кандидата через открытый Career API (без токена).
- **Поток C** - каналы доставки: MCP-сервер для рекрутёра и Telegram-бот для
  соискателя, чтобы решением могли пользоваться реальные люди без развёртывания
  инфраструктуры.

Сценарий `reopen` (пересмотр прошлых кандидатов при изменении условий) здесь
**не специфицируется**: его нормативный документ - `SDD-C07-REOPEN-CANDIDATES.md`.
C08 лишь включает готовый `reopen` в список инструментов MCP (§8.3) и в
`SKILL.md`.

## 1. Границы и совместимость

1. Команды C06 `reserve`, `search`, `dedup`, их контракты и тесты не меняют
   поведения. Расширение `search` (поток A) добавляет только новые опции и
   новые поля выдачи; при отсутствии новых опций выдача байт-в-байт прежняя.
2. К API Потока с токеном - только GET-запросы. Write-back отсутствует во всех
   потоках, включая Telegram-бот: бот не отправляет отклик за кандидата, а даёт
   ссылку на страницу вакансии карьерного сайта, где кандидат откликается сам.
3. Не используются чувствительные признаки (возраст, пол, фото, гражданство,
   семейное положение). Никакого скоринга «подходит/не подходит» - только
   детерминированный матчинг термов с evidence.
4. LLM используется только для: извлечения термов/фильтров из свободного
   текста и расширения синонимами (как в C06 `SKILL.md`), и для форматирования
   ответа пользователю. Фильтрация и ранжирование - детерминированные, в коде.
5. Зависимости: ядро остаётся stdlib-only. Единственная допустимая
   **опциональная** зависимость - `pdfminer.six` для извлечения текста из PDF
   (§5.4); её отсутствие деградирует функцию, но не ломает ничего.
6. Все новые данные с PII (кэш текстов резюме) хранятся только локально,
   каталог кэша добавляется в `.gitignore`.

## 2. Термины

- **CV-кэш** - локальный каталог с извлечёнными текстами резюме, по одному
  JSON-файлу на кандидата (§5.3).
- **Открытая вакансия** - вакансия, опубликованная на карьерном сайте и
  доступная через открытый Career API без токена (`docs/11-career-api.md`).
- **Профиль соискателя** - структурированный набор термов и фильтров,
  извлечённый из свободного текста кандидата (§6.2).
- **Канал доставки** - способ, которым конечный пользователь вызывает функции:
  LLM-скилл, MCP-сервер или Telegram-бот.

## 3. Архитектура доставки

Ядро остаётся CLI-скриптами (`scripts/talent_pool.py`, новый
`scripts/job_seeker.py`). Каналы - тонкие обёртки над теми же функциями:

| Канал | Пользователь | Установка | Приоритет |
|---|---|---|---|
| `SKILL.md` (Claude Code и совместимые агенты) | рекрутёр с LLM-агентом | уже работает, дополняется сценариями | есть |
| MCP-сервер stdio (§8) | рекрутёр с Claude Desktop / Cursor / любым MCP-клиентом | один блок JSON-конфига, без хостинга | 1 |
| Telegram-бот (§9) | соискатель | один процесс `python3` на любой машине компании; long polling, публичный IP и домен не нужны | 2 |

n8n/веб-приложение отклонены: требуют хостинг и настройку, что противоречит
цели «реальный рекрутёр подключает без автора». MCP-сервер выбран основным
каналом рекрутёра, потому что подключение - это 5 строк конфига в
`claude_desktop_config.json`, а Поток сам продвигает витрину ИИ-агентов:
формат «MCP поверх открытого API» им понятен.

## 4. Discovery (этап 0, до кода)

Зафиксировать ответы в обезличенных fixtures, как делает C07 §10 этап 0:

1. **Скачивание `cv_original`.** `GET /api/v3/applicants/:id` возвращает

2. **JSON карьерного API.** `GET /open/constructor/:id` документирован как

   (`docs/11-career-api.md`). Получить реальный ответ песочницы, зафиксировать
   поля, из которых извлекаются `id`, `title`, `department`, `city`, `salary`,
   `schedule`, `description` вакансии. Если конструктор недоступен на тенанте,

3. **URL страницы вакансии** для ссылки «откликнуться»:
   `{POTOK_OPEN_BASE_URL}/jobs/{id}` (HTML-страница с кнопкой отклика,

## 5. Поток A - полнотекст резюме

### 5.1 Команда индексации

```bash
python3 scripts/talent_pool.py cv-index --reserve-file /tmp/reserve.json [--cache-dir .cv_cache] [--limit N]
```

Вход - файл выдачи `reserve` (существующий формат C06). Для каждого кандидата:

1. Если в `CV_CACHE_DIR` уже есть свежий файл этого кандидата со статусом
   `ok` и тем же `source_url` - пропустить (идемпотентность).
2. Взять первый элемент `resumes[]` с непустым `cv_original`. Нет ни одного -
   записать статус `no_cv`.
3. Скачать файл (§5.2), извлечь текст (§5.4), записать кэш-файл (§5.3).

Итог в stdout - JSON: `{"indexed": N, "skipped_fresh": N, "no_cv": N,
"failed": N, "by_status": {...}}`. Ошибка одного файла не прерывает обход
(статус `download_failed` / `extract_failed` в кэш-файле), сетевые ошибки
подчиняются общим правилам C06 (timeout 30 c, backoff на 429).

### 5.2 Скачивание

`urllib`, `GET cv_original`, timeout 30 c. Сначала без `Authorization`; на
401/403 - повтор с `Authorization: Bearer {POTOK_API_TOKEN}`. Разрешены только
`https://` URL (на mock - `http://localhost`). Лимит размера файла - 10 МБ
(читать поток кусками, при превышении статус `too_large`). Редиректы -
стандартные для `urllib` (только на тот же протокол).

### 5.3 Формат кэш-файла

`{CV_CACHE_DIR}/{applicant_id}.json`:

```json
{
  "applicant_id": 4,
  "source_url": "https://.../resume.docx",
  "fetched_at": "2026-09-03T12:00:00Z",
  "status": "ok",
  "format": "docx",
  "text": "полный извлечённый текст ..."
}
```

Нормативные `status`: `ok`, `no_cv`, `download_failed`, `too_large`,
`extract_failed`, `unsupported_format`. При статусе не `ok` поле `text`
равно `""`. `CV_CACHE_DIR` добавляется в `.gitignore` в этом же изменении;
README получает предупреждение, что кэш содержит персональные данные и его
нельзя коммитить или пересылать.

### 5.4 Извлечение текста по расширению файла (без учёта регистра)

- `.docx` - stdlib: `zipfile` → `word/document.xml` →
  `xml.etree.ElementTree`. Текст - конкатенация `.text` всех элементов, тег
  которых оканчивается на `}t`; после каждого элемента с тегом на `}p`
  добавляется `\n`. Namespace-префиксы не хардкодить, сравнивать по суффиксу
  тега.
- `.txt` - прочитать байты, декодировать `utf-8`, при `UnicodeDecodeError` -
  `cp1251`, при повторной ошибке - `utf-8` с `errors="replace"`.
- `.pdf` - только если импортируется `pdfminer.six`
  (`from pdfminer.high_level import extract_text`). Если библиотека не
  установлена - статус `unsupported_format`, в stderr одно суммарное
  предупреждение «PDF пропущены: установите pdfminer.six» (не по одному на
  файл).
- Остальные расширения (`.doc`, `.rtf`, без расширения) -
  `unsupported_format`.

После извлечения: схлопнуть последовательности пробельных символов в один
пробел внутри строк, убрать пустые строки, обрезать текст до 200 000 символов.

### 5.5 Расширение `search`

Новая опция существующей команды:

```bash
python3 scripts/talent_pool.py search '<TERMS_JSON>' --reserve-file ... [--cv-cache-dir .cv_cache]
```

Без опции поведение прежнее. С опцией:

1. Для каждого кандидата выдачи, у которого есть кэш-файл со статусом `ok`,
   термы дополнительно матчатся по тексту резюме **тем же матчером C06**
   (по границам слов, многословный терм - все токены присутствуют).
2. Скоринг title/tags не меняется. Терм, совпавший только в резюме (не в
   title/tags), добавляет к существующему score кандидата `+1` один раз на
   уникальный терм.
3. В evidence кандидата добавляются элементы
   `{"source": "cv", "term": ..., "kind": "original|synonym", "quote": ...}`,
   где `quote` - фрагмент текста резюме вокруг первого совпадения, максимум
   120 символов, обрезанный по границам слов.
4. В summary выдачи добавляется блок
   `"cv_coverage": {"with_cv_text": N, "without": N}` - чтобы LLM честно
   сообщал, для какой части кандидатов полнотекст был доступен.

Кандидаты без кэша или со статусом не `ok` участвуют в поиске как раньше
(только title/tags) и не получают штрафа.

## 6. Поток B - режим соискателя

Новый файл `scripts/job_seeker.py`, stdlib-only, использует только открытый
Career API (без токена). Функции матчинга термов и HTTP-обвязка
переиспользуются импортом из `talent_pool.py`, а не копированием.

### 6.1 Получение вакансий

```bash
python3 scripts/job_seeker.py jobs-list
```

`GET {POTOK_OPEN_BASE_URL}/constructor/{POTOK_CONSTRUCTOR_ID}`. Из ответа
(поля уточняются на discovery §4.2) строится нормализованный список:

```json
[{
  "id": 42,
  "title": "Python Backend Developer",
  "department": "Разработка",
  "city": "Москва",
  "salary_from": 280000, "salary_to": 350000, "currency": "RUR",
  "schedule": "remote",
  "description": "текст описания без HTML-тегов",
  "apply_url": "https://{subdomain}.potok.io/open/jobs/42"
}]
```

HTML в описании вычищается stdlib-классом `html.parser.HTMLParser`
(собрать только текстовые узлы), затем нормализация пробелов как в §5.4.
Отсутствующее в ответе поле - `null`, не пустая строка и не ноль.

### 6.2 Контракт профиля соискателя

LLM (или бот §9) передаёт извлечённый из свободного текста профиль:

```json
{
  "terms": [
    {"term": "python", "kind": "original"},
    {"term": "питон", "kind": "synonym"},
    {"term": "django", "kind": "original"}
  ],
  "filters": {"city": "Москва", "schedule": "remote", "salary_from": 300000}
}
```

Формат `terms` идентичен входу C06 `search`. Все поля `filters` опциональны;
неизвестное значение не передаётся вовсе. LLM-инструкция расширения
синонимами - та же секция `SKILL.md`, что и для C06 (расширение
контекстно-зависимое, помечать синонимы `kind: "synonym"`).

### 6.3 Команда матчинга

```bash
python3 scripts/job_seeker.py jobs-match '<PROFILE_JSON>' [--jobs-file /tmp/jobs.json] [--top 10]
```

Без `--jobs-file` список вакансий запрашивается как в §6.1.

1. **Фильтры** (строгие, применяются до скоринга): `city` - равенство после
   `casefold`; `schedule` - равенство значений API; `salary_from` кандидата -
   вакансия проходит, если `salary_to` вакансии `null` или
   `>= salary_from` кандидата. Вакансия с `null` в поле фильтра не
   отбрасывается, а помечается `"filter_unknown": ["city"]` в выдаче.
2. **Скоринг** - сумма по уникальным термам:
   вес = (терм найден в `title`: 3, иначе в `department`: 2, иначе в
   `description`: 1) × (`kind == "original"`: 2, `synonym`: 1). Матчер - тот
   же, что в C06 (границы слов, все токены многословного терма).
3. Сортировка: score по убыванию, затем `id` по возрастанию. Нулевой score не
   попадает в выдачу.

Выдача:

```json
{
  "summary": {"jobs_total": 12, "matched": 3, "filtered_out": 4},
  "jobs": [{
    "id": 42, "title": "...", "apply_url": "...", "score": 8,
    "filter_unknown": [],
    "evidence": [
      {"source": "title", "term": "python", "kind": "original", "quote": "Python Backend Developer"},
      {"source": "description", "term": "django", "kind": "original", "quote": "...опыт с Django от 2 лет..."}
    ]
  }]
}
```

Правила quote - как в §5.5 п.3.

### 6.4 Красная линия потока B

Отклик не отправляется программно ни при каких условиях. Единственное
действие - показать `apply_url`. Персональные данные соискателя (его
свободный текст) не передаются в API Потока вообще: наружу уходят только
GET-запросы списка вакансий.

### 6.5 Fallback без конструктора

Если тенант не отдаёт JSON конструктора (discovery §4.2), `jobs-list`
поддерживает `--fallback-v3`: авторизованный `GET /api/v3/jobs` с фильтром
опубликованных на карьерном сайте вакансий (поле публикации уточняется по
`docs/02-jobs.md` при реализации). Это ломает свойство «без токена», поэтому
режим явно помечается в выдаче `"source": "v3_fallback"` и в README; для
Telegram-бота fallback допустим - бот и так хостится компанией, владеющей
токеном.

## 8. Поток C1 - MCP-сервер

### 8.1 Файл и транспорт

`scripts/mcp_server.py`, stdlib-only. Транспорт - stdio: JSON-RPC 2.0, одно
сообщение на строку stdin/stdout (newline-delimited). Любой лог - только в
stderr; stdout содержит исключительно JSON-RPC ответы. Функции вызываются
импортом из `talent_pool.py` / `job_seeker.py`, не через subprocess.

### 8.2 Минимальный протокол

Обрабатываются ровно четыре входящих типа; на прочие методы - ошибка
`-32601` (`{"jsonrpc":"2.0","id":...,"error":{"code":-32601,"message":"method not found"}}`):

1. `initialize` → ответ:
   ```json
   {"jsonrpc": "2.0", "id": 1, "result": {
     "protocolVersion": "2025-06-18",
     "capabilities": {"tools": {}},
     "serverInfo": {"name": "potok-talent-pool", "version": "1.0.0"}}}
   ```
2. `notifications/initialized` - без ответа (это notification, `id`
   отсутствует).
3. `tools/list` → `{"result": {"tools": [...]}}` со списком §8.3; каждый
   инструмент - `{"name", "description", "inputSchema"}` (JSON Schema,
   `additionalProperties: false`).
4. `tools/call` с `params: {"name": ..., "arguments": {...}}` → выполнить,
   вернуть
   `{"result": {"content": [{"type": "text", "text": "<JSON результата>"}], "isError": false}}`.
   Исключение внутри инструмента ловится, возвращается тот же формат с
   `isError: true` и текстом ошибки без стектрейса; сервер продолжает работать.

### 8.3 Инструменты

| name | Обёртка над | arguments |
|---|---|---|
| `potok_reserve` | `reserve` | `{}` |
| `potok_search` | `search` | `{"terms": [...], "cv": bool}` - при `cv: true` перед поиском выполняется `cv-index` по свежей выдаче резерва |
| `potok_dedup` | `dedup` | `{}` |
| `potok_reopen` | `reopen` (SDD C07 §8) | `{"request": <REQUEST_JSON C07 §4>, "top": int}` |
| `potok_jobs_match` | `jobs-match` | `{"profile": <PROFILE_JSON §6.2>}` |

`description` каждого инструмента переносит триггер-формулировку из
`SKILL.md`, чтобы MCP-клиент сам выбирал инструмент. Ошибки валидации входа
возвращаются как `isError: true`, а не как крэш процесса.

### 8.4 Подключение (в README)

```json
{
  "mcpServers": {
    "potok-talent-pool": {
      "command": "python3",
      "args": ["/abs/path/ai-agent-potok/scripts/mcp_server.py"],
      "env": {
        "POTOK_BASE_URL": "https://demo.app.potok.io/api/v3",
        "POTOK_API_TOKEN": "..."
      }
    }
  }
}
```

Приёмочная проверка - ручной прогон без клиента:
`printf '...\n' | python3 scripts/mcp_server.py` с последовательностью
`initialize` → `initialized` → `tools/list` → `tools/call potok_reserve`
против mock-сервера.

## 9. Поток C2 - Telegram-бот соискателя

### 9.1 Файл и цикл

`scripts/tg_bot.py`, stdlib-only (`urllib`, `json`, `time`). Long polling:

1. `GET https://api.telegram.org/bot{TOKEN}/getUpdates?timeout=50&offset={last_update_id+1}`
   (timeout `urlopen` - 60 c).
2. Для каждого сообщения - обработка §9.3, ответ через
   `POST .../sendMessage` (JSON-тело: `chat_id`, `text`,
   `parse_mode: "HTML"`, `disable_web_page_preview: true`).
3. Сетевые ошибки: пауза 5 c и продолжение цикла; бот не падает от одной
   ошибки. Остановка - Ctrl+C.

Публичный IP, домен и webhook не нужны - процесс работает с любой машины с
выходом в интернет. Это единственный компонент проекта, требующий постоянно
работающего процесса, и он опционален: конкурсное демо бота идёт против
mock-сервера.

### 9.2 Вызов LLM (извлечение профиля)

Raw HTTP к Anthropic Messages API, без SDK (сохраняем zero-dependency):

```
POST https://api.anthropic.com/v1/messages
Content-Type: application/json
x-api-key: {ANTHROPIC_API_KEY}
anthropic-version: 2023-06-01
anthropic-beta: server-side-fallback-2026-07-01
```

Тело:

```json
{
  "model": "claude-opus-5",
  "max_tokens": 1024,
  "fallbacks": "default",
  "system": "<промпт извлечения профиля>",
  "messages": [{"role": "user", "content": "<текст кандидата>"}]
}
```

Параметр `thinking` не передавать (у модели включён адаптивный режим по
умолчанию). Промпт извлечения требует ответ строго одним JSON-объектом
формата §6.2 без пояснений, с правилами синонимов из `SKILL.md`. Обработка
ответа:

1. Проверить `stop_reason`. При `"refusal"` - ответить пользователю «не могу
   обработать это сообщение, опишите, пожалуйста, желаемую работу» и не
   продолжать.
2. Взять text-блоки `content`, распарсить `json.loads` подстроку от первой
   `{` до последней `}`. При ошибке парсинга - один повторный запрос с
   добавленным сообщением об ошибке; при повторной неудаче - извиниться и
   попросить переформулировать.

Второй вызов LLM (опциональный) форматирует выдачу `jobs-match` в
человекочитаемый ответ; при недоступности LLM бот отправляет простой
шаблонный список «название - город - зарплата - ссылка», собранный кодом.

### 9.3 Диалог и ограничения

- Бот stateless: каждое сообщение обрабатывается независимо, история не
  хранится ни в памяти между сообщениями, ни на диске.
- `/start` → приветствие: что умеет бот, что он показывает только
  опубликованные вакансии и не отправляет отклик за пользователя.
- Текст длиннее 1000 символов - вежливый отказ с просьбой сократить.
- На один `chat_id` - не чаще одного запроса в 5 секунд (словарь
  `chat_id → last_ts` в памяти); при превышении - «подождите пару секунд».
- Логи - только `chat_id`, timestamp и статус обработки в stderr; текст
  сообщений не логируется.
- Список вакансий кэшируется в памяти на 10 минут, чтобы не дёргать Career
  API на каждое сообщение.

## 13. План реализации

Порядок - по соотношению «ценность для конкурса / риск для готового C06»:

- **Этап 5 - Telegram-бот** (§9): опциональный, последним - единственный
  компонент с внешними ключами.
- **Этап 6 - документация и демо**: README (запуск каждого канала, таблица §3,

## 14. Не входит в первую версию

- Отправка отклика за соискателя, любые POST в API Потока.
- Семантический поиск, embeddings, скоринг «релевантности» вне описанных
  детерминированных весов.
- Извлечение структуры из резюме (стаж, навыки как поля) - только полнотекст.
- `.doc`/`.rtf`, OCR сканов.
- Хостинг бота как сервис, webhook-режим Telegram, хранение диалогов.
- HTTP/SSE-транспорт MCP - только stdio.
- Мультитенантность: один процесс = один тенант Потока.

## 15. Риски и ограничения

- Формат ответа `/open/constructor/:id` не задокументирован - главный риск
  потока B; закрывается discovery §4.2 и fallback §6.5.
- Скачивание `cv_original` может требовать иной авторизации, чем API
  (подписанные URL с истечением) - закрывается discovery §4.1; в худшем случае
  поток A деградирует до текущего поведения C06 с честным статусом в кэше.
- Извлечённый текст PDF бывает шумным (колонки, переносы); матчер по границам
  слов устойчив к этому, но цитаты могут выглядеть рвано - допустимо для MVP.
- Telegram-бот несёт расходы на LLM-вызовы владельца бота; rate-limit §9.3 -
  минимальная защита. Публичный бот без ограничения круга пользователей в
  первой версии не рекомендуется в README.
- MCP-протокол зафиксирован на `protocolVersion: 2025-06-18`; несовместимый
  клиент увидит ошибку версии - в README указать проверенные клиенты
  (Claude Desktop, Claude Code).
