# SDD: C07 - повторный поиск среди прошлых кандидатов

Дата постановки: 2026-09-03. Заказчик: Дмитрий.

## 1. Цель

Помочь рекрутеру вернуться к кандидатам, отклонённым или завершившим работу по
похожей вакансии, когда условия найма изменились. Типовые изменения: выросла
зарплатная вилка, разрешили удалённую работу, расширили допустимый профиль,
изменили локацию или снизили требование к опыту.

Скилл отвечает не на общий вопрос «кто есть в резерве», а на вопрос:

> Кого из прошлых кандидатов теперь стоит пересмотреть и почему?

Основная ценность - ранжированный список с проверяемым объяснением изменения,
а не автоматическое решение об отказе или приглашении.

## 2. Границы и совместимость

1. Это **новый, отдельный сценарий** рядом с C06. Существующие команды C06
   `reserve`, `search` и `dedup`, определение резерва и их выдача остаются без
   изменений.
2. Режим read-only: только GET-запросы к API Потока. Скилл не добавляет
   кандидата на вакансию, не меняет этап, теги или комментарии и не связывается
   с кандидатом.
3. Скилл показывает рекомендацию для ручной проверки, а не делает вывод
   «кандидата ошибочно отклонили» или «кандидат точно подходит».
4. Не используются чувствительные признаки: возраст, пол, фото,
   гражданство, семейное положение и подобные поля.
5. Семантический поиск и embeddings не используются. LLM допускается только
   для извлечения условий из текста и контекстного расширения терминов; расчёт
   правил, фильтрация и ранжирование должны быть детерминированными.

## 3. Термины

- **Целевая вакансия** - новая или изменённая вакансия, под которую ищутся
  кандидаты (`target_job`).
- **Старая версия условий** - условия вакансии до изменения
  (`previous_criteria`). API не предоставляет историю полей вакансии, поэтому
  их передаёт рекрутер либо, с его явного подтверждения, они берутся из
  выбранной архивной вакансии.
- **Текущие условия** - условия после изменения (`current_criteria`). Это
  полное состояние сравниваемых полей, а не только изменившиеся значения.
- **Референсная вакансия** - архивная/предыдущая вакансия, по которой берутся
  прошлые кандидаты (`source_job_id`). Она может совпадать с `target_job`, если
  вакансию отредактировали, а не создали заново.
- **Прошлый кандидат** - кандидат с неактивным (`active=false`) AJS Join на
  референсной вакансии. Это не обязательно отказ: связь могла завершиться по
  другой причине.
- **Подтверждённая причина** - причина из `declination_reason_id`, если поле
  действительно присутствует в ответе AJS Join конкретного тенанта и успешно
  сопоставлена со справочником причин отказа.
- **Гипотеза переоткрытия** - проверяемое структурное изменение условий без
  подтверждённой причины отказа. Гипотеза не называется причиной отказа.

## 4. Пользовательский сценарий

Рекрутер может обратиться свободным текстом:

> По вакансии Python Backend #42 подняли вилку с 220-280 до 280-350 тысяч,
> разрешили remote и берём от 2 лет. Кого из прошлых отказов стоит пересмотреть?

Или в форме/структурированном вызове:

```json
{
  "target_job_id": 42,
  "source_job_id": 17,
  "previous_criteria": {
    "salary_to": 280000,
    "currency_type": "RUR",
    "schedule_type": "fullDay",
    "experience_type": "between3And6",
    "experience_minimum_years": 3,
    "role_terms": ["python", "backend"],
    "profile_terms_any": ["django"]
  },
  "current_criteria": {
    "salary_to": 350000,
    "currency_type": "RUR",
    "schedule_type": "remote",
    "experience_type": "between1And3",
    "experience_minimum_years": 2,
    "role_terms": ["python", "backend"],
    "profile_terms_any": ["django", "fastapi"]
  },
  "applicant_salary_currency": "RUR",
  "context_terms": {
    "salary": ["320000", "не меньше 320000"],
    "schedule": ["remote", "удалённо"],
    "experience_minimum": ["2 года", "от 2 лет"],
    "profile": ["fastapi"]
  },
  "applicant_url_template": "https://company.potok.io/applicants/{id}"
}
```

`role_terms` описывает неизменное ядро роли: кандидат должен совпасть со всеми
его термами. `profile_terms_any` - альтернативные допустимые профили:
достаточно совпадения с одним термом. Это разделение не позволяет ошибочно
представить добавление обязательного навыка как расширение условий.
`context_terms` - подтверждённый рекрутером контролируемый словарь для точного
поиска в тегах и комментариях. LLM может предложить его из свободного текста,
но не может незаметно добавить синонимы перед расчётом.

### 4.1 Обязательные входы

- `target_job_id` или явное новое описание вакансии;
- `source_job_id` либо подтверждение рекрутера, что история кандидатов должна
  браться из `target_job_id`;
- хотя бы одно поддерживаемое изменение между `previous_criteria` и
  `current_criteria` после нормализации.

Если старые условия неизвестны, скилл не заявляет, что условия «изменились».
Он предлагает выбрать референсную вакансию или ввести прежние условия.
Текущая карточка вакансии не может одновременно служить источником старых и
новых условий. Если `source_job_id == target_job_id`, `previous_criteria`
обязательно вводятся отдельно. Если ID целевой вакансии не указан, проверка
активной связи с ней неприменима и это явно указывается в результате.

Для `salary_unlocked` обязательны известная одинаковая `currency_type` старых
и текущих условий и явное `applicant_salary_currency` с тем же значением:
карточка кандидата содержит число `salary`, но не содержит валюту. Без этого
подтверждения зарплатный сигнал отключается.

В структурированном вызове явное описание передаётся как
`target_job_description: string`, выбор целевой вакансии как источника истории
задаётся как `use_target_as_source: true`. Если старые условия извлекаются из другой
вакансии, требуется `source_represents_previous_criteria: true`; при явно
заполненных `previous_criteria` это подтверждение не нужно и его наличие
запрещено: источником условий являются явные данные, а не карточка вакансии.
`applicant_salary_currency` является утверждением рекрутера о валюте поля
`salary` для всех кандидатов этого запуска, а не данными API.

### 4.2 Формат результата

Сначала краткий итог: сколько уникальных неактивных кандидатов получено,
сколько карточек проверено, сколько уникальных кандидатов исключено как
активные или нанятые (с отдельными счётчиками причин), и по каким изменениям
найден результат. При частичных данных каждый счётчик помечается как нижняя
граница, а не точное полное количество.

Затем таблица:

| Кандидат | Референсная вакансия | Подтверждённая причина | Что изменилось | Уверенность | Evidence |
|---|---|---|---|---|---|
| Анна, id 81 | Python Backend #17 | Ожидания по зарплате | Вилка 280k -> 350k, ожидание 320k | высокая | `applicant.salary`, старое и новое `salary_to` |
| Илья, id 95 | Python Backend #17 | Нет данных | FastAPI добавлен как допустимая альтернатива Django | средняя | `tags`: FastAPI; старые `profile_terms_any`: Django |

Для каждого кандидата обязателен ID. Ссылка на UI-карточку строится только по
настроенному `applicant_url_template`; API base URL нельзя выдавать за UI URL.
Если шаблона нет, вместо выдуманной ссылки выводится «ссылка не настроена».
Свободный текст комментария, если он использован, приводится короткой цитатой
с датой и пометкой «контекст», а не как установленная причина.
Итоговая уверенность кандидата равна максимальной уверенности его сигналов;
она не выводится из числового score.

## 5. Источники API и модель данных

| Данные | Endpoint | Назначение |
|---|---|---|
| Целевая и референсная вакансия | `GET /api/v3/jobs/:id` | Поля вакансии и этапы |
| Кандидаты референсной вакансии | `GET /api/v3/jobs/:job_id/ajs_joins` | Отбор неактивных AJS Join |
| Карточка кандидата | `GET /api/v3/applicants/:id` | `salary`, `city`, `title`, `tags` |
| Нанятые | `GET /api/v3/finalists` | Исключение нанятых кандидатов |
| Причины отказа | `GET /api/v2/declination_reasons` | Расшифровка `declination_reason_id` |
| Контекст | `GET /api/v2/events?applicant_id=:id` | Только по отобранным кандидатам |

C06 продолжает использовать существующий `POTOK_BASE_URL`, оканчивающийся на
`/api/v3`. Для C07 добавляется `POTOK_API_V2_BASE_URL`. Если он не задан, его
можно вывести только заменой завершающего `/api/v3` на `/api/v2`; при другом
формате `POTOK_BASE_URL` C07 завершает валидацию с ошибкой. Mock явно задаёт
оба base URL. Это правило не меняет URL существующих команд C06.

Discovery на песочнице проведён 2026-09-03 на реальном заведомо отклонённом
кандидате: `GET /jobs/:id/ajs_joins` **не отдаёт** `declination_reason_id` и
`declined_at` вообще (поля отсутствуют в ответе, а не `null`) — вопреки
документации модели. Реальный источник — `GET /api/v2/events?applicant_id=:id`,
событие `type: "Event::Decline"` c `job_id` целевой связки, поле
`properties.declination_reason_id`; дата отказа — `created_at` этого события.
Оба значения читаются из уже загружаемых для комментариев событий без
дополнительного запроса (см. `_fetch_comments_for` в `talent_pool.py`).
Если у тенанта и там нет `Event::Decline` с этим полем, блок «Подтверждённая
причина» выключается, а результат строится только на структурных изменениях
и помечается «причина отказа недоступна через API».

## 6. Алгоритм

### 6.1 Подготовка условий

1. Загрузить `target_job`, если указан ID, и объединить его поля с явно
   заданными `current_criteria`. Явно введённое рекрутером непустое значение
   имеет приоритет; `null` и отсутствующее поле оба означают «неизвестно» и
   не перекрывают API-значение.
2. Получить `previous_criteria` из ввода или из отличной от целевой архивной
   вакансии, которую рекрутер подтвердил как прежнюю версию условий. Не
   пытаться восстановить старую версию отредактированной вакансии из её
   текущей карточки.
3. Нормализовать контролируемые поля:
   - зарплата: неотрицательное число и `currency_type`;
   - график: значения `schedule_type` API;
   - опыт: целое неотрицательное `experience_minimum_years`; если явно задано
      только поддерживаемое API-значение `experience_type`, оно преобразуется из
     `noExperience`, `between1And3`, `between3And6`, `moreThan6` в нижнюю
      границу 0, 1, 3 или 6 лет. Явное число приоритетнее bucket и позволяет не
      потерять формулировку вроде «от 2 лет». Неподдерживаемое значение во
      внешней карточке считается неизвестным; в явном запросе отклоняется как опечатка.
   - город: строковый ID города;
   - термы: нормализованные `role_terms` и альтернативы
     `profile_terms_any`; `added_profile_terms` вычисляются как разность
     текущего и старого наборов, а не принимаются от LLM готовыми.
   Для термов используется Unicode `casefold`, regex `[^\w#+]+` как
   разделитель, удаление пустых значений и дублей с сохранением первого
   написания. Дефис является разделителем. Равенство наборов проверяется после
   нормализации.
4. LLM может извлечь эти поля из текста. Перед запуском скилл показывает
   распознанные изменения и просит уточнение при неоднозначности.
5. После нормализации вычислить diff. Одинаковые значения не являются
   изменением. Расширением считаются: рост `salary_to`, понижение
   `experience_minimum_years` и строгое расширение `profile_terms_any` при
   неизменном `role_terms`.
   Изменение графика само по себе не считается улучшением для конкретного
   кандидата: оно используется только вместе с причиной или прямым контекстом.
   Для города допустим отдельный структурный сигнал из документированного
   `applicant.city.id`. Понижение вилки, повышение требований и удаление
   допустимого профиля не создают сигналов.
   Изменение `role_terms` между старыми и текущими условиями не создаёт
   сигналов: ядро роли считается неизменным, а `new_terms_match` проверяет
   совпадение кандидата с текущими `role_terms`. Если ядро роли изменилось,
   рекрутер должен создать новую вакансию.
6. Отсутствующее поле и явный `null` оба означают «неизвестно», но не ноль,
   пустой набор или снятие ограничения. Diff строится только для поля, у
   которого известны обе стороны. Явное непустое значение запроса перекрывает
   API; `null` не затирает известное API-значение. Если после merge не осталось
   ни одного сравнимого поддерживаемого изменения, запуск останавливается с
   ошибкой валидации.
7. Ошибка запроса, malformed response или отсутствие нужного поля целевой либо
   референсной вакансии блокирует только зависящий от него diff. Если из-за
   этого не остаётся валидного изменения или нельзя подтвердить выбранную
   референсную вакансию, ранжированный результат не возвращается.

Приоритет источников одного текущего поля: явное значение
`current_criteria` > поле API `target_job`. Если вместо ID передан
`target_job_description`, вызывающий LLM/адаптер извлекает из него подтверждённые
значения в `current_criteria`; ядро правил не интерпретирует свободный текст.
Конфликт между ID в JSON и
одноимённой CLI-опции является ошибкой; CLI может только заполнить отсутствующий
ID. `use_target_as_source=true` и `source_job_id` взаимоисключающие, а
также `source_represents_previous_criteria=true` при совпадающих ID запрещены.
Если `previous_criteria` явно заполнены, `source_represents_previous_criteria`
также запрещён независимо от совпадения ID: подтверждение не нужно, а его
наличие создаёт неоднозначность о источнике условий.
Извлечённое из текста значение показывается рекрутеру до запуска правил.

### 6.2 Формирование кандидатов

1. Загрузить все AJS Join референсной вакансии с курсорной пагинацией.
2. Оставить только `active=false`.
3. Загрузить всех финалистов с курсорной пагинацией. Построить `hired_ids`,
   исключая состояния `cancel_hire` и `hire_canceled`, как в C06.
4. Если указан `target_job_id`, отдельно загрузить все его AJS Join и построить
   `target_active_ids` по `active=true` (даже когда целевая и референсная
   вакансии различаются). При совпадении вакансий переиспользовать полный
   ответ шага 1, а не делать второй запрос; частичный ответ в этом случае
   считается небезопасным и блокирует выдачу.
5. Исключить `hired_ids` и `target_active_ids`, затем загрузить полные карточки
   только оставшихся кандидатов. Повторяющиеся `applicant_id` дедуплицировать.
6. События загружать только для кандидатов, оставшихся после этих исключений,
   но не только для уже получивших другой сигнал: комментарий сам может быть
   единственным сигналом. Учитывать только `Event::Comment` с
   `event.job_id == source_job_id` и обходить все страницы ответа.

Счётчики исключений взаимоисключающие: сначала `hired`, затем
`active_on_target` среди оставшихся. Отдельно возвращаются
`candidate_ids_observed`, `cards_attempted` и `cards_loaded`; ошибка карточки
не маскируется как фильтрация кандидата.

Каждая страница валидируется до использования. Для safety-critical финалистов
обязательны корректные `applicant_id`, `state`, `has_next_page` и при
продолжении `page_next_cursor`; для target AJS Join - `applicant_id`, boolean
`active` и те же поля пагинации. Любой malformed item/page блокирует выдачу.
Malformed item/page референсной вакансии можно пропустить только со статусом
`partial` и `ranking_complete=false`.

### 6.3 Правила переоткрытия

Каждое срабатывание хранится отдельно как `reopening_signal`; один кандидат
может иметь несколько сигналов.

| Сигнал | Условие | Уверенность |
|---|---|---|
| `salary_unlocked` | Есть `applicant.salary`; старый потолок ниже ожидания, новый не ниже; валюты нормализованных старых/текущих условий и явно подтверждённая валюта ожидания совпадают | высокая |
| `location_unlocked` | Есть `applicant.city.id`; старый город отличается от города кандидата, новый совпадает с ним | средняя |
| `decline_reason_matches_change` | Есть подтверждённая причина, вручную сопоставленная с направлением реально произошедшего поддерживаемого изменения: зарплата, локация, график, минимальный опыт или профиль | высокая |
| `new_terms_match` | Есть хотя бы один `role_term`; кандидат совпал со всеми `role_terms` и хотя бы одним `added_profile_term`, но ни с одной старой альтернативой `profile_terms_any` | средняя |
| `context_mentions_change` | Явный тег кандидата или комментарий референсной вакансии буквально содержит один из контролируемых терминов конкретного изменения | средняя, только как контекст |

Термы сопоставляются самостоятельным детерминированным правилом C07,
совпадающим с текущей реализацией matcher C06: без совпадений по подстроке;
многословный терм совпадает, только если присутствуют все его нормализованные
токены. Порядок слов не учитывается. SDD C06 при этом не изменяется.

Нельзя создавать сигнал для графика или опыта из обычных полей карточки:
API не документирует предпочтительный формат работы и стаж в годах. Для них
требуется подтверждённая причина, явный тег или комментарий с прямой цитатой.
`applicant.city.id` позволяет создать `location_unlocked`, но не доказывает
готовность кандидата работать из этого города или отказаться от remote.
Для графика нет структурного сигнала вроде `location_unlocked`: единственными
путями создания сигнала остаются `decline_reason_matches_change` (при наличии
настроенного соответствия) и `context_mentions_change` (при точном совпадении
тега или комментария с `context_terms.schedule`).

Одна причина создаёт не более одного `decline_reason_matches_change`, даже если
сопоставлена нескольким изменившимся типам. Один тип сигнала учитывается в
балле один раз; несколько комментариев или термов расширяют evidence, но не
умножают вес. Явный тег графика, локации или опыта учитывается как
`context_mentions_change` и не становится подтверждённой причиной. Для
комментария evidence обязательно содержит короткую цитату, дату и ID события;
для тега - точное значение тега.

Если одна причина совместима с несколькими изменениями, единственный сигнал
содержит evidence для всех них в фиксированном порядке: `salary`, `location`,
`schedule`, `experience_minimum`, `profile`. Поле «Что изменилось» перечисляет
те же изменения; произвольный выбор одной категории запрещён.

Сопоставление причины проверяет направление изменения. Категория
`experience_minimum` применима только при снижении нижней границы опыта;
абстрактная причина «опыт» недостаточна, поскольку она может означать и
избыточный опыт. Категория `profile` создаёт сигнал только вместе с совпадением
кандидата по добавленной допустимой альтернативе. Зарплатная причина применима
только при росте потолка, остальные категории - только когда соответствующее
значение действительно изменилось.

`context_mentions_change` создаётся только по точному новому значению или
направленной фразе из подтверждённого `context_terms`. Общие слова вроде
«зарплата», «опыт», «город» или «график» сами по себе запрещены: они не
доказывают, что прежнее условие блокировало кандидата. Для категориального
изменения терм должен однозначно обозначать текущее значение (`remote`,
`удалённо`); для числового - новое/кандидатское значение либо направленную
фразу (`от 2 лет`, `не меньше 320000`). Для context-фраз используется более
строгое правило, чем для skills: нормализованные токены должны идти подряд в
том же порядке. Для однословного тега требуется точное равенство после
нормализации.
Для изменения профиля context term обязан совпадать с
`added_profile_terms`; неизменная старая альтернатива не создаёт сигнал.

### 6.4 Ранжирование

Базовый балл - сумма весов уникальных типов сигналов: высокая = 3, средняя =
2. Только при наличии хотя бы одного `reopening_signal` добавить `+1`, если
кандидат совпал со всеми нормализованными `role_terms` текущих условий по
описанному выше matcher. Пустой `role_terms` бонуса не даёт. Сортировка: балл
по убыванию, затем `declined_at` по убыванию (`null` после дат), затем числовой
ID кандидата по возрастанию.

Скилл всегда раскрывает составляющие балла. Нулевой балл не попадает в выдачу.

## 7. Работа с причинами отказа и комментариями

Причины отказа у компаний произвольные. Для повторяемого результата скилл
использует конфигурацию соответствий, а не угадывает смысл причины:

```json
{
  "salary": [12, 19],
  "schedule": [{"reason_id": 27, "from": "fullDay", "to": "remote"}],
  "location": [{"reason_id": 31, "from": "1", "to": "2"}],
  "experience_minimum": [8],
  "profile": [44]
}
```

Для числовых направленных категорий (`salary`, `experience_minimum`) переход
проверяется самим правилом. Для `schedule` и `location` в конфигурации
обязательна точная пара `from`/`to`; одного ID причины недостаточно.

На первом запуске агент показывает только причины, встреченные у кандидатов
текущей референсной вакансии, но отсутствующие в конфигурации, и предлагает
рекрутеру отнести их к одному или нескольким типам либо исключить.
Сопоставление применяется только после явного подтверждения рекрутера.
Конфигурация может быть передана в вызове; write-back в Поток отсутствует.
Само название причины считается подтверждённым после успешного разрешения ID
через справочник. Конфигурация типов нужна только для создания сигнала и не
меняет этот статус.

В `REQUEST_JSON` конфигурация передаётся как
`declination_reason_mapping: object` в формате выше. Альтернатива CLI -
`--declination-reasons-file PATH`. Одновременная передача inline-конфигурации и
файла запрещена как неоднозначная; отсутствие обоих отключает сигналы причин,
но не отображение разрешённых через справочник названий.

Комментарии не сканируются по всей базе. Они запрашиваются только для
кандидатов референсной вакансии, оставшихся после исключений, и фильтруются по
точному совпадению `job_id`. Ищутся исключительно термины, явно указанные
рекрутером для изменившегося поля: точные новые значения, направленные фразы и
навыки, например `удалённо`, `от 2 лет`, `320000`, `fastapi`. Совпадение
считается по правилам §6.3, а не подстрокой. Модель не классифицирует скрытые
причины по свободному тексту.
Загрузка событий атомарна для каждого кандидата: если не получена хотя бы одна
страница, все собранные в этом запросе context evidence отбрасываются, а ID
кандидата добавляется в `completeness.events.failed_applicant_ids`.

`applicant_url_template` должен быть HTTP(S)-шаблоном ровно с одним `{id}`;
другие placeholders запрещены. Значение не используется для API-запросов.

## 8. Интерфейс скилла

Новый сценарий в `SKILL.md`:

> Используй, когда рекрутер изменил условия вакансии и просит пересмотреть
> прошлые отказы, неактивных кандидатов или кандидатов с прежней похожей
> вакансии.

Новая команда реализации:

```bash
python3 scripts/talent_pool.py reopen '<REQUEST_JSON>' --top 20
```

`REQUEST_JSON` содержит структуру из §4. При необходимости можно передать
`--source-job-id`, `--target-job-id` и `--declination-reasons-file` по правилам
§6.1 и §7, но это не меняет интерфейс существующих команд.

Команда возвращает JSON-объект с полями `summary`, `candidates`, `warnings` и
`completeness`. Ошибки валидации входа завершают вызов до API-запросов с
ненулевым exit code. Человекочитаемую таблицу формирует скилл, а не CLI, чтобы
машинный контракт оставался стабильным.

### 8.1 Машинный контракт результата

```json
{
  "status": "ok",
  "summary": {
    "candidate_ids_observed": 12,
    "cards_attempted": 9,
    "cards_loaded": 9,
    "excluded_hired": 2,
    "excluded_active_on_target": 1,
    "lower_bound_fields": []
  },
  "candidates": [{
    "applicant_id": 81,
    "name": "Анна",
    "url": "https://company.potok.io/applicants/81",
    "source_job_id": 17,
    "declined_at": "2026-07-01T10:00:00Z",
    "confirmed_declination_reason": {"id": 12, "name": "Ожидания по зарплате"},
    "score": 3,
    "confidence": "high",
    "signals": [{
      "type": "salary_unlocked",
      "weight": 3,
      "evidence": [
        {"source": "applicant", "field": "salary", "value": 320000},
        {"source": "criteria", "field": "previous.salary_to", "value": 280000},
        {"source": "criteria", "field": "current.salary_to", "value": 350000},
        {"source": "criteria", "field": "currency_type", "value": "RUR"},
        {"source": "request", "field": "applicant_salary_currency", "value": "RUR"}
      ]
    }]
  },
  {
    "applicant_id": 95,
    "name": "Илья",
    "url": "https://company.potok.io/applicants/95",
    "source_job_id": 17,
    "declined_at": null,
    "confirmed_declination_reason": null,
    "score": 2,
    "confidence": "medium",
    "signals": [{
      "type": "new_terms_match",
      "weight": 2,
      "evidence": [
        {"source": "applicant", "field": "tags", "value": ["fastapi"]},
        {"source": "criteria", "field": "role_terms", "value": ["python", "backend"]},
        {"source": "criteria", "field": "added_profile_terms", "value": ["fastapi"]},
        {"source": "criteria", "field": "profile_terms_any_old", "value": ["django"]}
      ]
    }]
  }],
  "warnings": [],
  "completeness": {
    "source_joins": true,
    "finalists": true,
    "target_joins": true,
    "jobs": {"target": true, "source": true},
    "cards": {"attempted": 9, "loaded": 9},
    "reasons": true,
    "events": {"complete": true, "failed_applicant_ids": []},
    "ranking_complete": true
  }
}
```

Нормативные значения `status`: `ok`, `partial`, `blocked`. `partial` допустим
только при безопасной деградации из §9; `candidates` может содержать результат,
но при неполных source joins обязательно `ranking_complete=false`, а top-N
называется «top среди просмотренного подмножества», не глобальным top.
`blocked` всегда содержит пустой `candidates`, хотя бы один warning с полями
`code`, `message`, `scope` и `ranking_complete=false`; это не валидная пустая
выдача. Для warning кандидата добавляется `applicant_id`.

Каждый сигнал обязан содержать `type`, `weight` и непустой массив `evidence`.
Evidence содержит `source` (`applicant`, `job`, `criteria`, `request`,
`declination_reason`, `tag` или `event`) и релевантные `field`/`value`; для
события обязательны `event_id`, `quote`, `created_at`. Evidence обязано
покрывать все операнды правила, а не только совпавшее поле кандидата.
`confirmed_declination_reason`, `declined_at` и `url` могут быть `null`;
остальные показанные поля кандидата обязательны.

`ranking_complete=true` допустим, только если полностью загружены все
компоненты, способные изменить состав или score: source joins, карточки,
причины (если поле доступно), нужные события и все заявленные criteria diffs.
Любая безопасная деградация выставляет `status=partial` и
`ranking_complete=false`. `summary.lower_bound_fields` перечисляет счётчики,
для которых неизвестен полный tenant-wide итог. При неполных source joins это
как минимум `candidate_ids_observed`, `excluded_hired` и
`excluded_active_on_target`; `cards_attempted`/`cards_loaded` остаются точными
счётчиками фактически наблюдаемого подмножества.

Стабильные warning codes первой версии: `VALIDATION_ERROR`,
`SOURCE_JOINS_PARTIAL`, `FINALISTS_INCOMPLETE`, `TARGET_JOINS_INCOMPLETE`,
`JOB_UNAVAILABLE`, `CARD_UNAVAILABLE`, `REASONS_UNAVAILABLE`,
`EVENTS_INCOMPLETE`, `CRITERIA_INCOMPLETE` и `MALFORMED_RESPONSE`. В
`completeness` значения `target_joins` и
`jobs.target` равны `null`, если соответствующий ID не задан; `reasons=null`,
если tenant не отдаёт поле причины даже для известного отказа.

Exit code: `0` для `ok` и безопасного `partial`, `2` для ошибки входной
валидации, `3` для `blocked` из-за API/неполных safety-critical данных. При
кодах 2 и 3 stdout всё равно содержит JSON с `status: blocked`; diagnostics не
подменяют машинный результат произвольным текстом.

## 9. Ограничения

- У API нет истории изменения полей вакансии: без явных `previous_criteria`
  сравнение «было/стало» недостоверно.
- Неактивный AJS Join не всегда означает отказ.
- Наличие `declination_reason_id` в ответах надо проверить на живом тенанте.
- `salary` кандидата может отсутствовать, быть устаревшей или относиться к
  другой роли; валюта в карточке отсутствует. Даже при явном подтверждении
  валюты это рекомендация для контакта, не гарантия интереса.
- Текст резюме не разбирается. Матчинг обязанностей только по `title/tags` и
  прямому контексту комментариев.
- Доступ к комментариям может раскрывать внутренние заметки; результат должен
  показывать минимум нужной цитаты и соблюдать права доступа текущего токена.
- Частичная загрузка референсных AJS Join допустима: выдаётся найденное
  подмножество с предупреждением о неполном покрытии, кроме случая
  `source_job_id == target_job_id`. Частичная загрузка финалистов или AJS Join
  целевой вакансии небезопасна: невозможно гарантировать исключение нанятых и
  активных, поэтому ранжированный список не возвращается.
  Ошибка отдельной карточки исключает этого кандидата; ошибка причин отключает
  сигналы причин; ошибка событий отключает контекстные сигналы для затронутых
  кандидатов. Каждый случай отражается в `warnings` и `completeness`.
- Недоступная или malformed карточка целевой/референсной вакансии блокирует
  выдачу, если без неё нельзя подтвердить источник кандидатов или вычислить
  хотя бы один полный diff. Неизвестное значение нельзя заменять дефолтом.

- [x] При недоступности `declination_reason_id` функция остаётся полезной, но

- [x] Неполный список финалистов или активных AJS Join целевой вакансии

  референсная вакансия не является целевой.
- [x] `partial` и `blocked` соответствуют контракту §8.1 и не выглядят как
  полный глобальный top или валидная пустая выдача; неполные события одного
  кандидата не дают ему context signal.
- [x] Отсутствующие и `null`-критерии не превращаются в нули/пустые наборы и не

- [ ] Fixtures и автоматические тесты покрывают каждый сигнал, исключения,
