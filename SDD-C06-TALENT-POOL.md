# SDD: C06 — поиск по кадровому резерву + дедупликация базы

Дата постановки: 2026-08-18. Заказчик: Дмитрий. Дизайн зафиксирован в обсуждении той же даты (см. §3–4 ниже — не требуется перечитывать чат).

## 1. Цель

Собрать чат-скилл для LLM поверх открытого API «Потока», который закрывает боль C06 из `research/pains/PAIN-RESEARCH-REPORT.md` (приоритет 50, подтверждена и интервью, и широким исследованием):

1. **Главная ценность:** рекрутер свободным текстом описывает, кто нужен, — скилл находит подходящих кандидатов в кадровом резерве. У Потока нет вообще никакого механизма семантического/расширенного поиска (только точное совпадение по контактам/ФИО) — барьер копирования высокий.
2. **Бонус-функция:** скилл показывает дубли кандидатов в базе (одно и то же резюме заведено дважды). Понижена в приоритете 2026-08-25 — см. §1.1: у Потока уже есть per-card детект дублей, масштабировать его на всю базу для них не бог весть какая доработка, барьер копирования низкий. В питче не выдавать за равноценную половину продукта.

Read-only. Без вебхуков, без семантического поиска/embeddings, без записи в Поток.

Состав MVP зафиксирован 2026-08-21:

- LLM расширяет запрос синонимами/нормализацией перед матчингом («питон»→Python, «джун»→junior) — защита от пустой выдачи и усиление AI-составляющей заявки;
- из резерва исключаются нанятые финалисты (отменённый найм возвращается в резерв);
- парсинг резюме (`cv_original`) — за cut-line с явным триггером включения (см. §5).

## 1.1 Проверка пересечения с фичами Потока (2026-08-25)

В продукте Поток обнаружение дублей — **per-card, не глобальное**: открываешь конкретную карточку кандидата — если у него есть дубль, система пишет «найден возможный дубликат» и даёт кнопку «слить». Общего экрана/отчёта «вот все дубли в базе» нет. Это подтверждено пользователем на живом UI песочницы (не только по API — в API такой функции нет вообще, проверены все 39 эндпоинтов `docs/tools.json`, ни `merge`, ни `find_duplicates`).

Практическое следствие: обнаружение у Потока **реактивное** (сработает, только если рекрутер вручную открыл именно эту карточку) — на базе в сотни/тысячи кандидатов подавляющее большинство дублей никто не увидит, потому что до нужной карточки просто не доходят. Наш скилл закрывает именно это — проактивный массовый скан всей базы за один вызов. Пересечения с идеей C06 нет, разделение труда чистое: агент находит и показывает списком → рекрутер жмёт «слить» сам в Потоке (подтверждает решение §4 «Write-back: отсутствует»).

## 3. Факты об API (вшито, чтобы не перечитывать `docs/*`)

- Auth: Bearer-токен в `Authorization`. Rate limit: 100 запросов/10 сек на токен → нужен backoff на 429.
- `GET /api/v3/applicants` — список кандидатов. `per_page` до 100, максимум 10 000 записей глубины (page×per_page). Поля: `phones[]`, `email`, `title`, `tags[]`, `resumes[].cv_original` (это **URL на файл**, не текст). Точный фильтр `f[phones][]` / `f[emails][]` — батч до 50 значений, полное совпадение (нормализованный телефон, без `+`/пробелов).
- `GET /api/v3/applicants/:id` — полная карточка.
- `GET /api/v3/jobs?by_scope=all` — все вакансии компании, page/per_page.
- `GET /api/v3/jobs/:job_id/ajs_joins?page_size=100&page_cursor=...` — кандидаты конкретной вакансии, курсорная пагинация, поле `active` (true = в работе сейчас). **Глобального листинга ajs_joins нет** — только per-job.
- `GET /api/v3/finalists?page_size=100&page_cursor=...` — принятые кандидаты, курсорная пагинация, `page_size` до 100; в объектах есть `applicant_id` и `state`. Нанятые = все состояния, кроме `cancel_hire`/`hire_canceled` (отменённый найм возвращает человека в пул).
- `docs/tools.json` уже содержит готовые function-calling схемы: `list_applicants`, `get_applicant`, `get_job_ajs_joins`, `list_finalists` и другие. Использовать их как есть — не писать HTTP-клиент заново.

## 4. Архитектура (решено, не пересматривать без явной причины)

**Резерв** (кандидаты без активной вакансии сейчас и не нанятые):
```
GET /jobs?by_scope=all                                  → все вакансии
для каждой: GET /jobs/{id}/ajs_joins?page_size=100       → id кандидатов, где active=true → active_ids
GET /applicants?per_page=100 (полный обход)              → все кандидаты компании
GET /finalists?page_size=100 (полный обход)              → applicant_id нанятых (state ≠ cancel_hire/hire_canceled) → hired_ids
резерв = все кандидаты \ active_ids \ hired_ids
```

**Дедупликация** — на том же пуле всех кандидатов: группировка по нормализованному `phone` и отдельно по `email`. Группа с >1 разным `applicant_id` = дубль. Точное совпадение, без fuzzy-логики по ФИО (осознанно, см. §6).

**Поиск по резерву** — рекрутер пишет запрос свободным текстом («срочно нужен Python, remote»). LLM (не API «Потока») сначала нормализует и расширяет запрос: извлекает ключевые слова/навыки и добавляет синонимы/варианты написания («питон»→Python, «джун»→junior, «1С»→1C, «тимлид»→team lead). Расширенный набор термов матчится против `title` + `tags` кандидатов резерва (подстрокой/пересечением множества слов), ранжирует по числу совпадений, отдаёт топ-N со ссылкой на карточку и списком совпавших слов (evidence). В evidence различаются совпадения по исходным термам запроса и по добавленным синонимам.

**Формат взаимодействия**: чат-скилл, а не CLI-скрипт и не n8n-воркфлоу.

**Write-back**: отсутствует. Скилл только читает и отвечает текстом/таблицей, ничего не пишет в Поток (ни тегов, ни комментариев).

## 5. Осознанно отложено (не делать в MVP)

- **Парсинг резюме (PDF/DOC).** API отдаёт только `cv_original` — URL на файл, не текст. Матчинг идёт по `title`/`tags`, усиленному LLM-расширением запроса синонимами. **Cut-line:** если демо-запросы на fixtures дают пустую/слабую выдачу — парсинг тянется в MVP как первое расширение (скачать файл → pdf/docx → текст → LLM извлекает навыки → кэш).
- **Fuzzy-дедуп по ФИО** (Иван/Ваня, опечатки). Только точное совпадение phone/email.
- **Семантический поиск/embeddings.** Explicitly запрещён условиями (API не даёт), keyword-matching достаточно и укладывается в срок.
- **Write-back** (тег «дубль», тег «резерв», комментарий). Ничего не меняет в Потоке — read-only отчёт/ответ.
- **Фильтрация резерва по причине отказа** (чтобы не тащить в резерв реально непригодных). Резерв = «нет активного ajs_join и не нанятый» — исключаются только нанятые финалисты, без доп. логики по отклонённым.

## 6. Этапы работы

### Этап 1 — Скилл-обвязка
Артефакт: `SKILL.md` (или эквивалент по принятой в проекте структуре) — описание триггера, доступных функций, инструкция LLM по извлечению ключевых слов из запроса рекрутера и формату ответа (таблица кандидатов + evidence + ссылка на карточку).

### Этап 2 — Функции доступа к данным
Поверх готовых схем `docs/tools.json`:
- `build_active_ids()` — обход `jobs` + `ajs_joins`, собрать set `applicant_id` с `active=true`. Учитывать курсорную пагинацию и 429-backoff.
- `build_hired_ids()` — полный обход `finalists` (курсорная пагинация), собрать `applicant_id` со state ≠ `cancel_hire`/`hire_canceled`.
- `build_reserve_pool()` — полный обход `applicants`, минус `active_ids` и `hired_ids`.
- `find_duplicates()` — группировка по `phones[]` (каждый телефон кандидата) и по `email`.

### Этап 3 — Поиск и ранжирование
LLM нормализует и расширяет запрос (термы + синонимы) → матчинг расширенного набора к `title`+`tags`: посчитать пересечение с полями кандидата, отсортировать по убыванию числа совпадений, вернуть топ-N (например 10) с перечнем совпавших слов и пометкой, какие совпадения дали исходные термы, а какие — синонимы.

### Этап 4 — Демо
**Mock Potok API server** (по схемам `docs/tools.json`) + обезличенные fixtures — обязательный артефакт этапа: жюри воспроизводит демо без живого тенанта и токена автора. Fixtures: кандидаты с 2–3 заведомыми дублями, 1–2 финалиста (в т.ч. один с отменённым наймом), 3–5 «резервных» с разными title/tags под тестовые запросы — включая кейсы под синонимы («питон», «джун»). Два сценария демо: «покажи дубли в базе» и «срочно нужен X, кто есть в резерве». Настоящий API — опциональный smoke test.

### Этап 5 — Документация
README: как подключить токен, как запустить на fixtures и на реальном тенанте, явные ограничения (нет текста резюме, нет семантики, нет фильтрации резерва по причине отказа) — не выдавать решение за то, чем оно не является.

## 8. Риски

- **Rate limit на больших тенантах.** Обход всех вакансий+ajs_joins+finalists для построения резерва может быть долгим на базе с сотнями вакансий. Митигировать backoff-ом на 429; если обход не укладывается в разумное время — ограничить первыми N вакансиями и явно предупредить в ответе, что резерв построен частично.
- **Шум в резерве.** Попадут и реально непригодные отклонённые кандидаты (нет фильтра по причине отказа) — известное ограничение, зафиксировать в README, не решать в MVP.
- **Слабый сигнал матчинга.** `title`/`tags` беднее текста резюме — часть релевантных кандидатов может не найтись. Митигировано LLM-расширением запроса синонимами (в MVP); если и этого мало на демо — cut-line на парсинг резюме (см. §5).

## 9. Fallback-инструкции

- Если `by_scope=all` для `jobs` недоступен в песочнице — использовать `by_scope=active`; резерв в этом случае не увидит кандидатов с архивных/отменённых вакансий, пометить это в ответе скилла.
- Если обход упирается в rate limit до завершения — вернуть частичный результат с пометкой «резерв построен по первым N вакансиям, не полный», не блокироваться и не падать молча.
