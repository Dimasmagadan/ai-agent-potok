# Сценарий базовой интеграции

Стандартная схема интеграции Потока с внешней системой, которая обогащает кандидата: проверка СБ, тестирование, скоринг, оформление — любой процесс вида «кандидат дошёл до этапа → внешняя система отработала → результат вернулся в Поток».

По этой схеме построено большинство продуктивных интеграций Потока.

## Как это устроено

```
Поток                                Внешняя система
  │  1. Кандидат переведён на триггерный этап
  │──── webhook {id, applicant_id, job_id} ────▶
  │                                      │
  │◀─── 2. GET данные кандидата ─────────│
  │     (карточка, резюме, анкета СБ)    │
  │                                      │ 3. Внешняя система
  │◀─── 4. PUT workflow-статус ──────────│    делает свою работу
  │     «в процессе» / «пройдено»        │
  │                                      │
  │◀─── 5. Результат: документ / ────────│
  │     комментарий / обновление полей   │
```

Обе стороны активны: Поток шлёт вебхуки (push), внешняя система ходит в API (pull + запись).

---

## Шаг 1. Вебхук с триггерного этапа

Настраивается командой Потока (см. [15-webhooks.md](15-webhooks.md)): при переводе кандидата на согласованный тип этапа воронки Поток отправляет POST на ваш URL:

```json
{
  "event": "ajs_join/Отправка данных по кандидату на вакансию",
  "data": {"id": 51562161, "applicant_id": 42213690, "job_id": 1083910}
}
```

(`event` — имя, заданное при настройке вебхука; `id` — ID кандидата на вакансии.)

Отвечайте `200` — иначе Поток будет ретраить (до 14 раз).

## Шаг 2. Получить данные кандидата

По ID из вебхука заберите то, что нужно вашему процессу:

```
GET /api/v3/applicants/{applicant_id}          # карточка: ФИО, контакты, резюме
GET /api/v2/security_forms?job_id={job_id}&item_id={applicant_id}   # анкета СБ
```

`security_forms` возвращает заполненную кандидатом анкету; файлы (сканы паспорта и т.п.) приходят ссылками на S3.

## Шаг 3–4. Workflow-статус: показать прогресс в Потоке

Workflow — статусная модель поверх кандидата на вакансии, видна рекрутеру в карточке (вкладка «Статус подбора»). Внешняя система двигает статус, рекрутер видит прогресс не выходя из Потока.

```
PUT /api/v2/workflows/{workflow_name}.json

{
  "model_id": "51562161",        // ID кандидата на вакансии (ajs_join)
  "model_name": "AjsJoin",
  "transition": "send"           // ID перехода
}
```

Ответ: `{"state_id": "in_progress"}` — новый статус.

Типовая статусная модель (набор статусов и переходов настраивается под интеграцию):

| Статус | Название | Переходы из него |
|--------|----------|------------------|
| `initialized` | Не отправлялся | `send` → in_progress |
| `in_progress` | В процессе | `finish` → finished, `cancel` → canceled |
| `finished` | Пройдено | `reset` → canceled |
| `canceled` | Отменено | `resend` → in_progress |

На смену статуса можно повесить уведомления рекрутеру (настраивается правилами в Потоке).

## Шаг 5. Вернуть результат

Три способа, в зависимости от формата результата:

**а) Результат — документ** (отчёт о проверке, сертификат). Неочевидный момент: файл сначала **создаётся**, потом **прикрепляется** отдельным запросом через комментарий:

```
POST /api/v3/documents.json          # multipart: attach=<файл>, name, category
→ {"document": {"id": 4410048, ...}}

POST /api/v2/events
{
  "applicant_id": 42213690,
  "job_id": 1083910,
  "body": "Отчёт о проверке",
  "type": "Event::Comment",
  "attach_document_ids": [4410048]
}
```

Документ появится в ленте кандидата на вакансии. Подробнее — [06-documents.md](06-documents.md), [05-events.md](05-events.md).

**б) Результат — текст** (вердикт, скоринг): просто комментарий:

```
POST /api/v2/events
{"applicant_id": 42213690, "job_id": 1083910, "body": "Проверка пройдена, замечаний нет", "type": "Event::Comment"}
```

**в) Результат — данные полей** (уточнённые контакты, гражданство и т.п.): обновление кандидата:

```
PUT /api/v3/applicants/{applicant_id}
{"applicant": {"phones": ["79161234567"], "citizenship": "РФ"}}
```

Принимает все стандартные и динамические поля формы кандидата. Вложенные объекты-сущности через этот метод не редактируются.

## Чек-лист интеграции

1. Согласовать с командой Потока: триггерный этап, URL вебхука, авторизацию, workflow-модель.
2. Принимать вебхук, отвечать 200 сразу, обрабатывать асинхронно.
3. Дозапрашивать данные по ID из вебхука (Шаг 2).
4. Двигать workflow-статус, чтобы рекрутер видел прогресс (Шаги 3–4).
5. Возвращать результат документом/комментарием/полями (Шаг 5).
6. Дедуплицировать входящие вебхуки (ретраи!) и уважать rate limit — 100 запросов / 10 секунд.
