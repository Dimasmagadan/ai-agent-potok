# SDD: C09 - внутренняя мобильность (бот для сотрудников)

Дата постановки: 2026-09-03. Заказчик: Дмитрий.

Идея родилась из discovery по C08 Потоку B: открытый Career API
(`GET /open/jobs`) на реальной песочнице `ip-dyakonov-da.potok.io` отдаёт
честный 404 от бэкенда — `potok_career_site_enabled` у тенанта выключен
(подтверждено 2026-09-03, см. SDD-C08 §15). Публичный сценарий «соискатель
описывает себя боту» на этом тенанте нерабочий в принципе, и чинить нечего —
это конфигурация компании, не баг.

Альтернативный сценарий, не требующий карьерного сайта вообще: **внутренний**
Telegram-бот, которым компания сама раздаёт доступ только своим сотрудникам.
Сотрудник присылает боту своё резюме/описание себя, бот показывает открытые
вакансии компании, на которые он мог бы претендовать, и по запросу — чего
конкретно не хватает для конкретной вакансии. Внутренний режим принимает
сообщения только из личного чата от Telegram user ID из
`JOB_SEEKER_ALLOWED_USER_IDS`; группы и остальные аккаунты отклоняются до
LLM/API-запросов.

## 1. Отличие от C08 Потока B

C09 — не новый код с нуля, а **другой источник данных** для уже готового
`job_seeker.py`/`tg_bot.py`:

| | C08 Поток B (соискатель) | C09 (сотрудник) |
|---|---|---|
| Источник вакансий | `GET {OPEN}/constructor/:id`, без токена | `GET /api/v3/jobs`, авторизованный (`--fallback-v3`, уже реализован, SDD-C08 §6.5) |
| Аудитория | любой внешний человек с ссылкой на бота | только сотрудники (закрытая рассылка) |
| Видимость вакансий | только опубликованные на карьерном сайте | все вакансии компании, включая неопубликованные на карьерном сайте; конфиденциальные (`private: true`) — исключены по умолчанию (§4 п.5) |
| Риск токена | нет — API без токена | токен компании живёт на сервере бота, сотрудникам не виден |
| Отклик | ссылка на карьерную страницу | ссылка + (сотрудник и так внутри компании, отдельного "apply" не нужно) |

Discovery подтвердил, что путь данных уже работает на реальном тенанте:

```
$ python3 scripts/job_seeker.py jobs-list --fallback-v3
{"source": "v3_fallback", "jobs": [{"id": 9, "title": "Python-разработчик (Backend)", ...}, ...]}
```

Три реальные вакансии вернулись корректно (§2 ниже — что при этом нашлось
сломанным).

## 2. Найденные discovery проблемы в существующем `--fallback-v3`

1. **`description` всегда `None`.** `fetch_jobs_v3_fallback` в
   `scripts/job_seeker.py:61` не читает `job["description"]` из ответа
   `/jobs.json`, хотя поле там есть (проверено на реальных данных). Без
   описания скоринг по термам (§6.3 SDD-C08) находит совпадение только в
   `title`/`department` — большая часть текста вакансии не участвует в
   матчинге. То же самое поле нужно и для §3 (отчёт о пробелах).
2. **`key_skills` не используется.** `GET /jobs.json` отдаёт `key_skills`
   (в реальных данных пока пустой список, но поле есть и предусмотрено
   моделью, `docs/02-jobs.md`) — не подмешивается ни в скоринг, ни в §3.
3. **`city` — сырой ID, а не имя.** В `fetch_jobs_v3_fallback` `city` берётся
   как есть (`"1"`, `"2"` на реальном тенанте) и кладётся в то же поле, что в
   `fetch_jobs_constructor` содержит человекочитаемое имя
   (`city.get("name")`, `job_seeker.py:45`). `_apply_filters` (`job_seeker.py:92`)
   сравнивает `filters["city"]` через `casefold()` как имя — с сырым ID это
   **никогда не совпадёт**, фильтр по городу для `--fallback-v3` тихо не
   работает. Сотрудник называет город словом («Москва»), а `job.city` —
   числовой ID. Известный справочник `GET /api/v3/dictionaries/cities` **не
   подходит**: он оперирует UUID, не совпадающими по формату с числовыми ID
   в `job.city` на этом тенанте — два разных справочника. Правильный
   источник имён неизвестен; первый шаг реализации — discovery-запросы,
   какой эндпоинт реально отдаёт имена для этих числовых ID (другой ключ
   словаря, другое поле в самом `/jobs.json` и т.п.). Если резолв найден —
   в вывод кладётся имя строкой; пока (или если) не найден — `city` во
   внутреннем режиме принудительно даёт `filter_unknown`, а не тихое
   несовпадение. Критерий приёмки различает эти два исхода: «100%
   filter_unknown» — допустимое состояние только при задокументированном
   отрицательном результате discovery, а не молчаливый дефолт.

   **Discovery проведён 2026-09-03 на реальном тенанте `demo.app.potok.io`.**
   Результат отрицательный, подтверждённого резолва не найдено:
   - `GET /api/v3/dictionaries/cities` — не подходит, ID в формате UUID
     (`00d5e24a-...`), тогда как `job.city` — короткая числовая строка
     (`"1"`, `"2"`); два разных справочника, подтверждено запросом.
   - `GET /api/v3/dictionaries` (полный список, 38 записей без пагинации
     дальше) — нет записи с числовыми ID городов.
   - `GET /api/v3/business_units` документирует `city: {"id": "1", "name":
     "Москва"}` (`docs/14-staffing.md`) — тот же числовой формат, что и
     `job.city`, лучший кандидат по формату. На песочнице `demo.app.potok.io`
     эндпоинт отвечает `200` с пустым `objects: []` — модуль штатного
     расписания не содержит данных для проверки на этом тенанте, сопоставление
     `id → name` не подтверждено фактическими данными.
   - `GET /api/v3/demands`, `GET /api/v3/staffing_items/paged` — тоже пустые
     на этом тенанте, city нигде не встречается.

   Решение: `fetch_jobs_v3_fallback` не строит резолв на неподтверждённом
   предположении — `job.city` принудительно `None` (→ `filter_unknown` в
   `_apply_filters`/`unknown_fields` в `jobs-gaps`) для всех вакансий из
   `--fallback-v3`, независимо от режима (это касается и внешнего C08:
   раньше сравнение молча не совпадало из-за формата, теперь явно помечается
   unknown — строго корректнее прежнего поведения). Апгрейд: если у компании
   включён модуль штатного расписания с данными, следующий шаг — сверить
   `business_units[].city` вживую и, если совпадает, включить резолв через
   него.
4. **Фильтр `career_site_published` противоречит цели C09.**
   `fetch_jobs_v3_fallback` пропускает вакансии с
   `career_site_published: false` (`job_seeker.py:70`) — правильное поведение
   для C08 (эмуляция карьерного сайта), но для C09 оно вырезает ровно те
   внутренние/неопубликованные вакансии, ради которых режим и затевается
   (таблица §1). Функция получает параметр (например,
   `published_only=True` по умолчанию — поведение C08 не меняется);
   внутренний режим передаёт `False`. Отдельно от этого фильтра — вакансии
   `private: true` (см. §4 п.5 и §8).

Всё это — не архитектурные проблемы, а недоделанный маппинг полей в уже
существующей функции; чинится в её теле, без новых абстракций.

## 3. Новая функция: отчёт о пробелах по вакансии

Симметрично `jobs-match` (даёт совпадения), нужен отчёт о несовпадениях для
конкретной вакансии — то, что просил заказчик: «чего не хватает для такой-то
вакансии».

```bash
python3 scripts/job_seeker.py jobs-gaps '<PROFILE_JSON>' --job-id 9 [--jobs-file ...] [--fallback-v3]
```

Профиль — тот же контракт §6.2 SDD-C08 (`terms`+`filters`). Алгоритм:

1. Найти вакансию по `id` в списке (тот же источник, что `jobs-match`); если
   не найдена — `{"error": "job_not_found"}`.
2. Для каждого управляемого поля, где вакансия задаёт требование, а профиль
   его не покрывает или не проходит его, добавить один пункт `gaps`:
   - `salary`: `filters.salary_from` профиля **выше**, чем `salary_to`
     вакансии — сотрудник хочет больше, чем максимум вилки. Это то же
     направление сравнения, что уже в `_apply_filters`
     (`job_seeker.py:105`). Обратная ситуация (профиль просит меньше, чем
     вакансия платит) — не gap, а нормальный матч. →
     `{"field": "salary", "job_value": <salary_to>, "profile_value": ..., "message": "вилка вакансии до X, вы указали ожидание от Y"}`.
   - `city`: `job.city` резолвится (см. §2 п.3) и не совпадает с
     `filters.city` (если оба известны).
   - `schedule`: `job.schedule` не совпадает с `filters.schedule` (если оба
     заданы).
   - `terms`: термы вакансии (`title`+`key_skills`, как ядро роли — не весь
     `description`, чтобы не выдавать общие слова за требование), которых нет
     ни среди `original`, ни среди `synonym` термов профиля.
3. Отсутствующее поле у профиля (пользователь не сказал ни слова про зарплату
   или город) — это `unknown`, а не `gap`; не выдумывать нехватку там, где
   просто нет данных ни с одной стороны. Выводится отдельным списком
   `unknown_fields`, чтобы бот мог прямо спросить об этом сотрудника.
4. Пустой `gaps` при непустых сопоставленных полях — валидный ответ «вы
   подходите по всем проверяемым критериям» (не путать с `unknown_fields`
   непустым при нулевом матчинге).

Формат ответа:

```json
{
  "job": {"id": 9, "title": "Python-разработчик (Backend)"},
  "gaps": [
    {"field": "salary", "job_value": 200000, "profile_value": 250000, "message": "вилка вакансии до 200000 ₽, вы указали ожидание от 250000"},
    {"field": "terms", "missing": ["django"], "message": "в требованиях вакансии есть django, в вашем профиле не найдено"}
  ],
  "unknown_fields": ["city"]
}
```

## 4. Бот: изменения в `tg_bot.py`

Переиспользуется весь цикл §9 SDD-C08 (long polling, извлечение профиля через
Anthropic API, rate-limit, отсутствие логов текста); от полного stateless во
внутреннем режиме есть одно отступление — память последнего профиля, п.4.
Меняется:

1. Источник вакансий — `fetch_jobs_v3_fallback` вместо
   `fetch_jobs_constructor`; включается флагом окружения
   `JOB_SEEKER_MODE=internal` (по умолчанию `external`, поведение C08 не
   меняется). Внутренний режим требует `POTOK_API_TOKEN`/`POTOK_BASE_URL` —
   без них бот отказывается стартовать с понятной ошибкой, а не падает на
   первом сообщении.
2. `/start` во внутреннем режиме — другой текст: бот компании, показывает
   вакансии компании (включая неопубликованные на карьерном сайте), не
   согласие на публичную рассылку резюме наружу. Обязательный дисклеймер:
   текст сообщений отправляется в Anthropic API для извлечения профиля — для
   внешнего соискателя (C08) это подразумевалось контекстом, сотруднику
   внутреннего бота это надо сказать явно.
3. Второй интент диалога — «чего мне не хватает для вакансии N». Отдельный
   regex-парсер не пишется: сообщение и так уходит в LLM за профилем, поэтому
   существующий промпт извлечения расширяется одним опциональным полем
   `target_job` (свободный текст — номер или название вакансии, как его
   упомянул сотрудник; поле отсутствует, если вакансия не упомянута).
   `target_job` затем сопоставляется со списком вакансий по `id`/`title`
   (простое включение подстроки, casefold); при однозначном совпадении —
   `jobs-gaps`, при отсутствии или неоднозначности — обычный `jobs-match` с
   припиской, какие вакансии похожи по названию. Это устойчивее regex:
   «чего не хватает для позиции бэкендера» не совпадёт по регулярке с
   «Python-разработчик (Backend)», а LLM это нормализует бесплатно.
4. Память последнего профиля. Бот C08 stateless, но естественный диалог C09
   двухшаговый: сообщение 1 — резюме, сообщение 2 — «чего не хватает для
   вакансии 9?». Без профиля во втором сообщении `jobs-gaps` посчитал бы
   пробелом всё подряд. Вводится минимальное состояние: in-memory dict
    `Telegram user ID -> последний валидный профиль` (перезаписывается каждым успешным
   извлечением, живёт только в памяти процесса, на диск не пишется — 
   обещания приватности C08 §9 не нарушаются; рестарт бота память очищает,
   это допустимо). Если во втором сообщении LLM вернул `target_job`, но
   профиль пустой/не извлёкся — берётся сохранённый; нет и его — бот просит
   сначала описать себя. Во внешнем режиме (C08) словарь не используется —
   поведение byte-for-byte прежнее.
5. Вакансии `private: true` (конфиденциальные — флаг проставляется при
   создании вакансии) **исключаются из выдачи бота по умолчанию**:
   конфиденциальный найм и замена действующего сотрудника — ровно те
   случаи, когда показ всем сотрудникам недопустим. Явный флаг окружения
   `JOB_SEEKER_INCLUDE_PRIVATE=1` включает их обратно, если компания это
   осознанно допускает; README объясняет риск.
6. Ограничение аудитории проверяется до обработки сообщения: оператор задаёт
   `JOB_SEEKER_ALLOWED_USER_IDS` с числовыми Telegram user ID сотрудников;
   бот принимает только личные чаты от этих ID. README объясняет настройку.

## 7. Не входит в первую версию

- Автоматическая подача заявки на внутренний переход (write-back).
- История прошлых запросов сотрудника, аналитика по частым «пробелам»
  (кадровая аналитика на этих данных требует отдельного решения о
  приватности).
- Уведомления о новых подходящих вакансиях (нужен long-running scheduler,
  не однократный polling-бот).
- LLM-анализ пробелов по `description` вакансии. Честное ожидание от v1:
  пока `key_skills` на реальном тенанте пуст, term-gaps сводятся к токенам
  `title` и малоинформативны («в профиле нет слова "разработчик"»).
  Действительно полезный ответ на «чего мне не хватает» — сравнение
  `description` с профилем через LLM (инфраструктура в боте уже есть) —
  осознанно отложен: для CLI-версии детерминированный diff правильнее, а
  для бота это кандидат №1 на v2.

## 8. Риски и ограничения

- Токен компании живёт на сервере бота — при компрометации сервера
  скомпрометирован весь API Потока (кандидаты, резюме, зарплаты), не только
  список вакансий. Это уже так для рекрутёрских потоков C06/C07 через MCP —
  новый риск только в том, что аудитория бота (все сотрудники) шире, чем
  аудитория MCP (рекрутёр). Рекомендация в README — отдельный токен с
  минимальными правами, если Поток это поддерживает (не проверено).
- `jobs-gaps` может задеть чувствительную тему («вам не хватает опыта») —
  формулировки должны быть нейтральными, как в C07 §4 (не «вы не подходите»,
  а «вакансия ожидает X»).
- Конфиденциальные (`private: true`) вакансии намеренно скрываются
  (конфиденциальный найм, замена действующего сотрудника и т.п.). Решение
  принято в §4 п.5: исключаются из выдачи по умолчанию, включаются только
  явным `JOB_SEEKER_INCLUDE_PRIVATE=1`. Остаточный риск: сам факт
  существования флага в README — компания должна включать его осознанно.
- Память последнего профиля (§4 п.4) держит извлечённый профиль сотрудника
  в RAM процесса до перезаписи/рестарта. Это слабее гарантий C08
  («ничего не хранится вообще»), но не пишется на диск и не логируется;
  README фиксирует это отличие внутреннего режима.
